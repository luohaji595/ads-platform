# 06 · 规则引擎深挖：跨平台规则库与可搬运参数

> 任务来源：用户指令「这个规则引擎才是最值钱的，去继续挖掘渗透其他平台寻找价值」。
> 定位：不是模块 4 开工，而是对模块 3（规则引擎+审批）的**横向扩产**——把其他平台的规则类型、算法公式、默认阈值、状态机、安全机制全部挖出来，形成一份可直接落代码的"规则库"。
> 证据分级：【A】官方文档给出具体公式/数值，或可读源码；【B】官方文档描述机制但无公式；【C】营销文案推断；【D】未公开。
> 已覆盖平台：Scale Insights、Ad Badger、Teikametrics、Perpetua、PPC Entourage（判定不可挖）、GitHub 开源实现（dsh-scale-commander）。

---

## 0. 结论先行（5 条最值钱的发现）

1. **最优 bid 不是"ACOS 超标就降 %"，而是一组闭式公式**。Scale Insights 公开了三条：有销售额用 `bid = (销售额/点击) × 目标ACOS`；无销售额但有售价用 `bid = 售价 × 目标ACOS / 点击数`（**点击越多自动双曲衰减，天然替代固定 step**）。第 3 条是 IvyeaOps 完全没有的，且实现成本极低。
2. **"花费闸门"是反直觉但极正确的保护**：当 `花费 < 售价 × 目标ACOS` 且 `当前 bid < 最优 bid` 时**不动手**。含义：还没花到"一个订单的允许成本"，而你的出价已经低于上限，抬价没意义。这条能消掉大量低点击关键词的无效调整噪声。
3. **目标出价必须做"归一化"**，否则算出来的 bid 会被 Amazon 侧的 placement 加价与 Dynamic Up&Down 放大，实际 ACOS 系统性偏离。公式已公开：`归一化 bid = 目标 bid × (100 ÷ (100 + placement 加价%))`，动态因子同理。
4. **成熟的"目标 × 盈亏锚点"双输入模型**（Teikametrics）：ACOS Limit = 广告前毛利率（盈亏平衡线），Goal 决定允许在锚点的哪个百分比区间出价——Product Launch 100–125%、Grow 95–100%、ROAS/Profit 1–100%、Liquidate 100–150%。同一套引擎，用目标语义调制激进度，比单一 `factor×margin` 更贴近运营语言。
5. **回滚有两种成熟范式，都不需要"逆向操作"**：①**执行前快照 + 反向写回**（IvyeaOps `snapshot_json`、Scale Commander `rollback()` 按 runId 逆序还原 before 值，且回滚本身也审计）②**事件区间自动复位**（Ad Badger：定时事件结束后 bid 自动恢复原值，"no cleanup rules required"）。我们模块 3 已有①，缺②。

## 1. 规则引擎的四种架构范式（决定我们抄哪种）

| 范式 | 代表 | 机制 | 我们是否采用 |
|---|---|---|---|
| **确定性规则引擎** | Scale Insights、IvyeaOps | 条件(AND) → 动作 → 限额；算法注册表；每天/每小时跑 | ✅ **主力**（模块 3 已有骨架，本文件扩规则库） |
| **纯算法黑盒** | Bids by Badger、Teikametrics Predictive AI | 单一算法每日/每小时重算所有 bid，用户只能调目标/上下限 | ⚠️ 部分采用（我们不做 ML，但保留"每天全量重算"的调度） |
| **建议流 + 人工接受** | Perpetua Recommendations、Teikametrics Smart Filters | 系统只出建议，人点接受；接受后可能自动执行 | ✅ **强烈建议增补**（比"逐条审批工单"更轻的人工成本） |
| **人工覆盖 + 到期回收** | Perpetua Bid Adjustments、Ad Badger Automatic Reset | 允许人强制指定 bid/倍率并设**实验时长**，到期自动恢复 | ✅ **增补为模块 3 第二类工单**（补 D4 缺口） |

> 关键洞察：**"规则引擎"和"AI 引擎"的产品差异不在算法强弱，而在"人能否在每一步看到 before→after 和算术过程"**。Scale Commander 的设计说明写得很直白：preview 和 apply 必须是**同一段纯函数**算出来的，"a preview cannot drift from execution"。我们照这个原则写：**候选生成 = 计划 = 预览 = 执行输入，同一份数据对象，不做二次计算**。

## 2. 规则数据的统一 Schema（可直接建表 / 定 DTO）

综合 Scale Insights 的四槽模型 + IvyeaOps 的注册表 + Scale Commander 的纯函数设计，统一成：

```
Rule {
  id, kind,                     // 算法类型（见 §3 的 11+5 种）
  name, enabled,
  priority,                     // 同类型多条时决定先后
  scope: {accountId, campaignId?, adGroupId?, targetId?},
  params: {...},                // 算法专属参数（§3）
  criteriaProfileId,            // 条件判据（可复用，AND 逻辑）
  limits: {minBid, maxBid, maxChangePercent, daysToObserve},
  window: {daysToAnalyze, daysToIgnore},
  schedule: {cron|hourly, timezone},
  dedupe: stackable | mutuallyExclusive,
  assignedVia: direct | inheritedFromObjective
}
CriteriaProfile { id, name, conditions: [{metric, op, value|min|max}] }   // op ∈ ≥ ≤ > < = between
Action { kind, entityType, entityId, before, after, reason, calculation[], metrics{} }
```
- **`calculation[]` 是必须字段**（Scale Commander 每条动作都带 `{step, expression, value}`），它是审计、UI 展开、AI 复核（模块 3 的三重 LLM）共同的证据源。**没有算术步骤的候选一律不生成**。
- 条件判据语言只需 6 个运算符（`≥ ≤ > < = between`）+ 数值指标 key，能覆盖 Scale Insights 与 Teikametrics 全部公开规则。

## 3. 规则库：可直接照抄的 16 类规则

### 3.1 Bidding（出价调整）— 核心
**三条最优 bid 公式**（Scale Insights 官方，【A】；Scale Commander 已实现为 `optimumBid()`）：

| 场景 | 公式 | 说明 |
|---|---|---|
| 有销售额 | `bid = (keyword 销售额 ÷ 点击) × 目标ACOS` | = RPC × 目标ACOS。Ad Badger 原文同源："your bid (CPC) should be set to your ACOS target percentage of your average RPC" |
| 有售价、有订单 | `bid = 售价 × 目标ACOS × (订单 ÷ 点击)` | = 售价 × 目标ACOS × CVR。例 $20×0.30×0.20 = $1.20 |
| **无销售额（最值钱）** | `bid = 售价 × 目标ACOS ÷ 点击` | 例 $20×0.30=$6 可花 → 10 点击时 $0.60、12 点击时 $0.50。**点击数累积即自动衰减**，无需 step |

**花费闸门**（【A】）：`若 spend < 售价 × 目标ACOS 且 current_bid < optimum_bid → 跳过（不抬价）`。

**归一化四步**（【A】，仅 SP + Target ACOS 模式）：
1. 算 optimal bid
2. 套 min/max 得 capped
3. 归一化：先乘 Dynamic Up&Down 因子（如 ×0.90），再除 placement 加价 → `bid × (100 ÷ (100 + modifier%))`（TOS 50% → ×100/150；100% → ×0.86；200% → ×0.57）
4. 按单次涨跌幅限制把 current 移向归一化目标

**参数**：`targetAcos`(1–500, 默认30)、`maxChangePercent`(0–100, 默认10)、`minBid`(默认0.02，Amazon 全局地板)、`maxBid`/`bidCap`、`useSuggestedBid`（以 Amazon 建议价封顶）、`daysToObserve`（冷却：近 N 天改过的对象跳过）。

**Bidding 规则的两种范式**（【A】，选型关键）：
- 范式A「算最优价」：逐关键词各自算目标价，落地更精细，但依赖 RPC/售价/COGS 数据。
- 范式B「ACOS 对比直接 ±%」：实现简单，但 Scale Insights 明确列为**反模式**：①提高 TOS 加价会推高整体 ACOS，被规则误读为"表现差"→ 错误降价 ②**平均 CPC ≠ 当前 bid**（历史高价期点击拉高 avg CPC），导致 ACOS 超标时仍应抬价、ACOS 达标时仍可能降价。
- 我们的选择：**A 为主（有毛利数据时），B 为兜底（无 COGS 时）**，且 B 必须带冷却期（Scale Insights 预设 7 天、Ad Badger 观察 7 天）。

### 3.2 否词（Negative）
**四槽设计**（Scale Insights，【A/B】）：①聚合来源（ASIN 全部同 ASIN 广告 / 单活动内 / 单 ad group / 自定义组可跨活动）②判据 ③否定匹配类型（negativeExact/negativePhrase）④目标 ad group。
- 官方参照阈值：`0 单 且 spend ≥ $10`（Spam Slaying）、`≥20 clicks 且 0 单`、`低 CTR 且 0 单`、`ACOS ≥ 50%`、商品定向 `≥5 clicks 且 0 单`。
- **Ad Badger Negative Nightly Hunt 三模板**（【A】）：Block Bad CTR Non-Converters / Block High-Click Non-Converters / Block High-Spend Non-Converters；自定义 7 步向导：层级(ad group/campaign) → 源活动 → 匹配类型 → **时间窗与判据（示例：近 30 天 Orders=0 且 Spend>$15）** → 频率(星期几) → 命名。
- 必带 **Never-Negatives 保护名单**（Ad Badger 原文提示：跑大范围否词前先查，防止误伤品牌词）。

### 3.3 单词否词（Negative Word / N-gram）
拆词 → 跨搜索词聚合单词表现 → 以 **negativePhrase** 加否。
- 官方阈值：单词 `≥25 clicks 且 0 单`（Scale Insights 与 Ad Badger 同值，【A】）。
- 案例（Scale Insights 官方）：Resistance Bands 产品，"bike" 112 clicks/$47.63 + "choke" 129 clicks/$31.05，这两个词跨 194 个搜索词共 241 clicks、$78.66、0 单。
- 参数：`minWordLength`(默认3)、`protectedWords`（白名单，命中跳过）。
- **坑（必须写进实现注释）**：否定单数会连带否定复数变体（否定 "turners" 也砍掉 "spatula turner"）。

### 3.4 收割（Import / Harvesting）
搜索词 → 在**现有** ad group 新建关键词或商品定向。
- 参数：`matchType`(exact/phrase/broad)、`bidPercentOfCpc`(10–500, 默认100 → **初始 bid = 搜索词 avgCPC × 100%**)、`maxKeywordsPerRun`(默认50，防关键词膨胀)、`targeting`(true=建商品定向)。
- 排序：按订单数降序取前 N。去重：同 adGroup+同词+同匹配类型跳过。支持 **Revert** 撤销。
- 判据分档（Scale Insights 预设，【A】）：Discovery 档 `≥2 单`；Sales 档 `≥5 单 且 CVR ≥ 15%`；本活动内补收 `≥3 单 且 ACOS ≥ 80%`→建 Exact。
- 官方警示：一个活动累积巨量关键词会**摊薄预算**，故必须有 `maxKeywordsPerRun`。
- **配套"毕业否定"**：收割成 Exact 后，在原 Phrase/Broad 组对该词加 negativeExact（搜索词隔离），这是 Scale Insights Discovery 预设的标准动作。

### 3.5 复活（Revive）
定义：曾经表现好、现在没流量（dead）的关键词，**逐步抬 bid 直到重新 active 或触顶**。
- dead 判据：近 N 天（默认 30 天）impressions < `activeImpressions`（默认 1）。
- 抬价依据：用**历史表现**（最早可得数据 → 3 天前聚合，可至 180 天）算 optimum bid，按 `maxChangePercent`（默认 **5%**，比 bidding 的 10% 更保守）逐步逼近。
- 范围：仅 SP 手动关键词（Scale Insights 矩阵【A】）。
- **坑（源码注释级）**：小 bid 抬幅被四舍五入吃掉——$0.20 抬 2% = $0.204 → 仍为 $0.20，规则空转。实现时必须检测"步长四舍五入后无变化"并 skip 且给出原因。

### 3.6 黑名单 / 白名单
- 黑名单：预置无关词表 → 自动写入 negativeExact 或 negativePhrase。
- 白名单两级（【A】）：**Exact Whitelist** 阻止 Blacklist/Negative/Negative Word 把该词否为 exact；**Phrase Whitelist** 阻止否为 phrase，但**不保护包含该短语的长词**（白名单 "spatula" 挡不住 "spatula turner"）。
- 优先级：Exact Whitelist 抵消 Negative Exact List 同词，但**不抵消** Negative Phrase List。
- 反哺机制：Negative / Negative Word 规则带 "Add To Blacklist" 勾选，可把自动否定**累积**成黑名单（越跑越省）。

### 3.7 状态（Status）
按表现 pause/enable 活动与 ad group。
- 参照阈值（Scale Insights Bulk Auto，【A】）：ad group `ACOS ≥ 50% 且花费 ≥ $20` → 停；`0 单 且花费 ≥ $15` → 停；**归因数据更新后 ACOS ≤ 30% → 自动重新启用**（自动复活，闭环）。
- 冲突警示：同一 ad group 同时有 dayparting 与 status 规则时，**dayparting 覆盖 status**（Scale Insights 官方明说）。

### 3.8 日预算（Daily Budget）
- 执行时点：**站点时区当天开始**（Scale Insights）/ 午夜跑（官方行为）。
- 参数：`baseline`（基准，可选）、`minBudget`/`maxBudget`（官方建议必设 max）、`daysToAnalyze`（≤90）、`daysToIgnore`、**`daysToObserve`（改动后观察 N 天不再动）**、`dayOfWeekMultipliers`（按星期几差异化）。
- Scale Commander 实现顺序（可抄）：baseline → 星期几倍率 → 逐条匹配判据依次乘 `(1 + adj%/100)` → 夹到 min/max → 与当前值差 < 0.01 则跳过。

### 3.9 位次（Placement）
分别对 **TOS / Product Pages / Rest of Search**（SB/部分 SP 另有 Business）建规则：`若 TOS ACOS < 20% → TOS 加价 20%`。
- 参数：`placement`、`targetModifier`(0–900, 默认50)、`incrementPercent`/`decrementPercent`(默认10)。
- 多规则协作两档 `Days to Observe`（【A】）：**"This Rule's Placement Only"**（只看本位次近期是否被改）/ **"Any Placement, Any Action"**（看活动内任一位次；且该规则执行后，同轮其他 placement 规则不再执行）。
- 上游约束：Amazon SP/SB 位次乘数合法区间 **0–900%**（Teikametrics 官方表，【A】）。

### 3.10 分时（Dayparting / Ad Scheduling）
两种控制（【A】）：①整段时间 **On/Off**（关广告组）②**百分比 bid modifier**（保持开启，base $1.00 +10%→$1.10，-20%→$0.80）。**0% 调整=不改 bid，但若该小时同时 enable ad group，状态变更仍生效**。
- Ad Badger 三种 Change Type：`Bid Amount ±$`、`Bid Percent ±%`、`Enable/Pause Campaign`；两种 Frequency：**SPECIFIC**（连续块，可跨午夜）、**RECURRING**（按天重复，可从 22:00 到次日 02:00 单条配置）。
- Scale Commander 的 `optimum` 模式（自动推导）：从小时表现推 -- 某小时订单数 ≥ `minHourlyOrders`(默认1) 则开，其余暂停；小时倍率与该小时 ACOS 相对账户均值的优势成正比。
- **关键实现陷阱（Scale Insights 原文，【A】）**：小时加价是叠加在 base bid 上的**临时值，任何"改 bid"动作都会清空它**。bidding rule 抬 20% 时用 base $1.00 算出新 base = **$1.20**（不是 $1.10×1.2）；改**状态**不会重置小时调整。→ 我们的 bidding 与 dayparting 必须互斥或明确约定谁覆盖谁（Ad Badger 做法：开 dayparting 自动关掉该活动的 bidding 算法）。

### 3.11 默认出价（Default Bid）
仅适用**老式无 4 个定向组的 Auto 活动**；有 close match/loose match/substitutes/complements 四组的，应走 Bidding 规则（【A】）。

### 3.12 组合预算闸（Portfolio Budget Condition）
Bidding 规则可挂前置条件：组合预算用量阈值（最高 **200%**）+ 回看期（默认 **7 天**，最高 180 天）；**回看期内任一天达到阈值 → 本轮跳过调价**（防预算吃紧还抬价）。

### 3.13 排名联动条件（Organic / SP Rank）
Bidding 规则可加**自然排名 + 广告排名**条件（【B/A】）：数值越小越好；必须在 Rank Tracker 追踪该词；**仅 SP 精确匹配**（不适用 broad/phrase/ASIN 定向/SB/SD）；数据取当天或昨天。
- 三个玩法：①有机位差 + 盈利 → 抬价抢排名 ②有机位好 → 降价省广告费 ③SP 位好但有机差 → 维持广告竞争。
- 官方警告：**排名条件必须与表现指标组合**，不能单看排名（否则给不赚钱的词抬价）。

### 3.14 低效词抑制 / 试探状态机（Ad Badger，最值钱的非线性机制）
bid 到 min bid 的两个触发：①有单但持续超目标 ACOS ②高点击无单。到 min 后：
- Scenario 1：在 min bid 达成目标 ACOS → 保持运行（理想态）。
- Scenario 2：仍在 min 表现差 → **抑制该词一段时间**；抑制长短取决于**活动整体**：活动优于目标 ACOS → 进入**激进测试模式**（对被抑制词反向抬价试探）；活动超目标 ACOS → 保守，抑制更久。
> 这套"抑制 + 按账户健康度决定是否试探"的双层状态机，IvyeaOps 与 Scale Insights 都没有显式实现，是本文件最值得新增的一类规则。可用状态字段实现：`suppressed_until`、`suppress_count`、`last_probe_at`。

### 3.15 人工覆盖 + 到期回收（Perpetua Bid Adjustments）
允许对指定词施加 ①固定 bid 或 ②bid 倍率，并**设实验时长**，到期自动结束；结果（无论好坏）回流作为后续调参依据。
- 与我们的工单体系融合：新增工单类型 `experiment`，字段 `{target, mode: fixed|multiplier, value, expires_at, auto_revert: true}`，到期由调度器自动还原并生成一条审计记录。
- 这是 **D4（回滚机制）的产品化答案**：不是"后悔药"，而是"有时限的人工意志"。

### 3.16 关键词独立加速（Perpetua Keyword Boost）
把选中词搬进独立 campaign + 专属 ACOS 目标与预算 + TOS 乘数，冲 TOS/自然排名。
- 限制（【A】）：不能选 PAT/类目定向；期间不做 keyword harvesting；不能再叠 placement 乘数；不能在 Custom Goal 建；**原活动里该词在 boost 期间临时归档**（防同词互抢）。
> 本质=「冲排名活动结构」的标准模板，适合新品期与冲刺期，不建议长期。

## 5. 各平台机制差异对照（抄谁、不抄谁）

| 维度 | Scale Insights | Ad Badger | Teikametrics | Perpetua | IvyeaOps |
|---|---|---|---|---|---|
| 引擎类型 | 确定性规则 × 11 算法 | 算法(BBB) + 2026 新增 IF/THEN/WHEN | 专有 AI + 目标语义 | 专有 AI + 建议流 | 确定性五杠杆 |
| 出价公式公开 | ✅ 三条公式 + 归一化 | ✅ "bid = RPC × target ACOS" | ❌（仅 min_bid 公式与 Goal 区间） | ❌ | ✅ RPC×target，含 step cap |
| 执行频率 | 每天一次；dayparting 每小时；预算按站点日 | 每日（+dayparting） | **每小时**（AMS Streaming） | 未公开 | 手动/定时 |
| 自动否词 | ✅ 4 源聚合 + 单词跨词 | ✅ Nightly Hunt 模板 | ✅ Actions 过滤器（建议流） | ❌ **故意不做** | ✅ 基础否词 |
| 回滚 | Change Logs（可查不可逆） | **事件结束自动复位** | 无公开 | 实验到期回收 | ✅ snapshot 反向写回 |
| 人类覆盖 | Preset/Clone/Simulator | Custom Algorithm | Snooze/Dismiss/Review 模式 | **Bid Adjustments 限时实验** | 工单三道闸 |
| 预览 | Preview + Strategy Simulator | 无（直接生效） | Review 模式 | Recommendations | dry-run |
| 独特资产 | 归一化公式 / 排名条件 / 白名单两级 | 抑制-试探状态机 / 三档否词模板 | Goal×ACOS Limit / bid exploration 限速 | 不做否词的架构哲学 / KWB | 三道闸 + snapshot |

**取舍结论**：
- **公式层抄 Scale Insights**（三条最优 bid + 归一化 + 花费闸门 + 窗口双参数）。
- **状态机层抄 Ad Badger**（抑制/试探 + 事件自动复位 + 三档否词模板）。
- **目标语义层抄 Teikametrics**（ACOS Limit = 毛利率锚点，Goal 修饰区间）。
- **人机协同层抄 Perpetua**（不做无脑否词的哲学 + 限时人工覆盖 + 建议流）。
- **安全层保留 IvyeaOps**（三重 LLM 复核 → 确定性 guardrail → 人工确认 → 快照回滚 → 熔断），并补"建议流/Review 模式"降低人工负担。
- **不抄**：Teikametrics/Perpetua 的专有 AI（不可复现）；Entourage 的模板式自动化（无公开规则）。

## 6. 建议在我们引擎里新增的 6 条规则（改动量排序）

| # | 规则 | 价值 | 实现成本 | 依赖 |
|---|---|---|---|---|
| 1 | **无单关键词连续衰减公式** `bid = 售价×目标ACOS÷点击` | 替代固定 step，减少调整次数且更贴近真实盈亏 | ★（一个函数） | 需商品售价/COGS |
| 2 | **花费闸门**（spend < 售价×目标ACOS 且 bid<optimum → 跳过） | 消掉大量噪声候选，减少工单量 | ★ | 同上 |
| 3 | **bid 归一化**（÷ placement 加价、× dynamic 因子） | 修正系统性 ACOS 偏离 | ★★ | 需同步 campaign 的 placement 与 bidding strategy |
| 4 | **抑制-试探状态机** | 处理"降到地板价仍不赚"的长尾词，避免一刀切否定 | ★★★ | 需新增 state 字段与 3~7 天调度 |
| 5 | **Goal × 盈亏锚点**（Launch/Grow/Profit/Liquidate 区间） | 让同一套规则表达"新品激进/清库激进" | ★★ | 需毛利数据 |
| 6 | **限时人工覆盖 + 到期自动还原** | 补 D4，支持人工意志又不留手尾 | ★★ | 需调度器 + 审计 |

## 7. 开源参照实现（已 clone 并读源码，【A】）

**`Jegozhou/dsh-scale-commander`**（Node.js/JS，MIT，2026-10）——把 Scale Insights 的 11 算法落成纯函数，**结构与我们目标高度同构**：
- `package/src/shared/algorithms.js`（866 行）：11 个 `evaluate*` 纯函数 + `optimumBid()` + `isNegligibleRaise()`（花费闸门）+ `stepToward()`（涨幅 cap）+ `roundBid()`（4 位小数、夹到 0.02 地板）+ `analysisWindow()`（≤365 天）+ `dedupeActions()`（同实体只动一次）。
- `package/src/shared/criteria.js`（191 行）：6 运算符条件 DSL + 校验（`between` 需 min≤max）。
- `package/src/host/engine.js`（899 行）：`rollback(runId)`——**逆序还原每条的 before 值**，回滚本身再写一条审计；`REVERSIBLE_VALUE_KINDS` 区分"值回写"与"创建类动作（删除）"。
- `package/src/host/schema.sql`：21 张表——`rules / criteria_profiles / assignments / objectives / runs / run_actions / schedules / audit_log / metrics_daily / hourly_metrics / search_terms / negatives / sync_state` 等。
- 设计原则原文："**the plan a person reviews must be exactly the plan that executes**……preview 与 apply 用同一段纯函数，preview 不可能与执行漂移"；"Applying requires `confirm: true`"；"Sandbox accounts never touch Amazon"。
> 可搬运点：动作对象带 `calculation[]`、`dedupeActions`、`rollback` 逆序语义、`confirm: true` 硬开关、hourly_metrics 表结构。这几点与我们模块 2/3 的产出可直接对接。

## 9. 对模块 3 产出的修订建议

1. **规则数从 5 → 11**：新增 Import(收割已部分有)/Revive/Status/DailyBudget/Placement/Dayparting/DefaultBid/Blacklist-Whitelist——其中 **Revive / Placement / DailyBudget / Dayparting** 对我们最实用，建议进 P0。
2. **bidding 公式升级**：现有 `new_bid = RPC × target` 保留，新增"无单衰减公式"与"花费闸门"。
3. **冷却期语义细化**：从"近 N 天动过就跳过"升级为 Scale Insights 的**双参数窗口**（`daysToAnalyze` + `daysToIgnore`）+ 规则级覆盖全局。
4. **审批形态补一条**：除"逐条工单"外，增加 **Review 模式集合批准**（一次接受一批候选），否则日常运维会被工单淹没（Teikametrics/Scale Insights 均为此形态）。
5. **回滚补第二条路径**：限时人工覆盖到期自动还原（Ad Badger/Perpetua），进入 `schedules` 调度。
