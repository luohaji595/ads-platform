## 一、总体架构结论（可搬运的骨架）

1. **SQLite 多库分文件，不单库也不上服务器**：每个服务域一个 `.sqlite3` 文件（users.sqlite3 / audit.sqlite3 / token_daily 等），统一放在 `data_dir`（`server/app/core/config.py:142`，env `IVYEA_OPS_DATA_DIR`，默认 `<root>/data`）。分库的好处：审计/计量等保留策略不同的数据可单独备份导出（audit.py 注释原话）。
2. **无 ORM、无集中迁移**：schema 用代码内 `CREATE TABLE IF NOT EXISTS` 散布在各服务文件里；`core/db_migrations.py` 只有 59 行，"现有表=version 0，破坏性变更往后追加版本"。个人级工具完全够用，抄这个决策。
3. **连接三件套**（每个 `_connect()` 都一样，照抄）：`PRAGMA journal_mode=WAL` + `busy_timeout=10000` + `foreign_keys=ON`，`isolation_level=None`，`sqlite3.Row`。
4. **缓存=参数哈希→整包 JSON**（`lingxing_cache` 表）：应对上游 API 限流（我们对应 Ads API 报表配额），默认 TTL 1800s，面板重复查看零调用。
5. **数据集注册表驱动**（`lingxing_data.py` 的 `READ_DATASETS`）：加一个数据源=加一条注册项（label/group/route/method/params schema/columns），零面板代码。我们的四级报表接入层可直接套用此模式。

## 三、通用审计层（core/audit.py，比 lingxing_audit 更泛化）

`audit_log` 表：ts, actor_id/actor_name, module, action, target, outcome, detail, request_id；三个降序索引（ts / module+ts / actor+ts）。三条铁律值得照抄进我们所有模块：
1. **审计失败绝不拖垮业务**：写流水失败只 warning 不上抛；
2. **流水里不能有凭据**：`_INLINE_SECRET` 正则把 `--token=xxx`/`Bearer xxx` 替换为 `***`；
3. **独立库文件**（audit.sqlite3），保留/备份策略与业务数据分开。

## 四、备份机制（core/backup.py，350 行，四取舍全抄）

1. 用 SQLite 官方在线备份 API `conn.backup()`，不 cp 文件（WAL 模式下 cp 可能丢最近事务），不停服，包里不需要 -wal/-shm；
2. 分层：默认只备"丢了拿不回"的（各库+配置+技能），可再生的大文件（图片/日志）要显式 include_media；`backups` 目录本身永不入包（防指数滚雪球）；
3. 密钥要么 AESGCM+PBKDF2(240k轮) 加密后入包，要么不入包并在 manifest 标注；
4. 恢复先 dry_run 报告会覆盖什么，显式确认才落地。

## 五、AI 智能体侧（模块7 预埋）

- **会话存储**（agent_session_service.py）：`agents`（可执行后端注册表）、`agent_sessions`（会话，含 parent_id 分支/token_estimate/resume_target 外部续聊指针）、`agent_messages`（id/session_id/seq/role/kind/source/content/meta_json）、`agent_summaries`（滚动摘要）。seq+session_id 索引。
- **工具桥**（ivyea_ops_tools.py，844 行）：后端功能包装成 MCP 工具清单（home/market/playbook/ad_audit/listing 等 40+ 工具），带 bridge token 鉴权 + module 级访问控制 + 返回值 24000 字符截断——这就是模块7 "AI 只读分析→产出待批清单"的骨架：AI 调工具读库，写操作走 lingxing_op_ticket 工单。
- **用量计量**（token_archive.py `token_daily`）：PK(day, source, agent, model)，字段 sessions/input_tokens/output_tokens/cache_read/cache_write/credits——AI 层成本核算表。
- **证据溯源**（evidence_trace.py）：从结论回源报表原始行（csv/xlsx），"原样返回不加工、匹配不到要明说"，MAX_ROWS=40。设计哲学原话："做不到溯源，证据页数字和模型编的数字在界面上长得一模一样"。模块7 必抄。

## 七、已落地的第一版实现（2026-11-14，ingest 包）

模块1 的取数管道已按本节定稿落地，代码在 `/Users/baoyanan/自动化广告平台/ingest/`：

| 文件 | 作用 |
|---|---|
| `jijia_client.py` | 积加开放平台 REST 客户端：钥匙串取 appId/appKey → `/api_token` 换 accessToken → `sign=md5(json+appKey)` → **强制直连**（`--noproxy '*'`，积加校验出口 IP）→ 60s 节流 → 401 自动刷新重试 |
| `schema.sql` | `dim_market` + 四张事实表 + `run_log`；`PRAGMA journal_mode=WAL`；事实表统一带 `row_hash` / `raw_json` / `source` / `ingested_at` |
| `ingest.py` | `DATASETS` 注册表驱动（加数据集=加一条注册项，与 IvyeaOps `READ_DATASETS` 同构）；**逐日拉取**；`ON CONFLICT DO UPDATE` 幂等；`run_log` 记 pages/fetched/written/status/note |
| `README.md` | 命令、四接口表、9 条踩坑、字段口径 |
| `verify.py` | 数据质量核验：覆盖区间 / 每日行数（找缺日）/ 主键重复 / 金额汇总与异常值 / run_log |
| `launchd/com.baoyanan.ads-ingest.plist` | 每天 06:10 拉昨日（`--start yesterday --end yesterday`） |

**首轮跑通结果（marketId 7 / 2026-11-01～11-13 / 13 天）**：campaign 637 行、keyword 706 行、searchterm 908 行、placement 1,488 行；13 天全覆盖、主键重复 0、异常值 0；合计 cost \$4,002.02 / clicks 4,079 / orders 74 / sales \$10,097.71 / ACOS 39.6%。幂等验证：同区间重跑行数不变（251→251）。

与本节定稿的三处偏差（都是实测逼出来的）：
1. **不做跨库拆分**：首版全部放一个 `ads.sqlite3`（dim+fact+run_log）。audit / tickets 两个独立库等模块3 真正开始写操作时再拆——现在拆只是空表。
2. **缓存表暂缓**：`lingxing_cache` 式"参数哈希→整包 JSON"缓存暂未建，因为积加接口不支持翻页、按天单查本身就是最细粒度，重复调用可由 `run_log` 判断跳过。
3. **`raw_json` 必存**：字段口径还没完全稳定（`targetingType` 枚举、`state` 含义、零值语义按接口不一致），保留原始行才能在不重拉的前提下重算。

另有三条**接口层硬约束**（已写入 `ingest.py` 与 03 文档 §3.2.3，属于模块1 的发现但直接影响模块2 主键设计）：
- `endDate` 是**排他上界**，拉 D 当天必须传 `(D, D+1)`，否则静默丢最新一天；
- 分页参数（`page`/`pageNo`/`offset`）被服务端忽略，只能逐日单查；
- `count` 上限 500（campaign `count=1000` 报 40004，placement `count=999` 报 50099）。
