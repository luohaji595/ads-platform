## 一、为什么"确定性规则 + 审批"而不是全自动

- 模块1 总原则：AI/规则**只产建议，写入必须过闸**。MAP 官方同款："read-only by default、write opt-in、AI proposes changes. You approve them. Every edit is logged."【B】
- IvyeaOps 源码注释（lingxing_operate.py:1-17）："A write never happens casually"——每个变更先成 ticket，三道闸全过才执行【A】。
- **v2 补一条更重要的理由**：外部平台的默认阈值是为「月花 5 万美元以上的成熟账户」调的。本账户日花 $190、日单 2.14、单词年化 668 点击【M】——照抄默认值的后果不是"不够优化"，是**误杀**（§4.6 有实测）。所以规则必须薄、闸必须厚。

## 二、引擎架构

### 2.1 统一 Schema（06 §2，可直接建表）

```
Rule {
  id, kind,                     // 30 类之一（§三）
  name, enabled, priority,
  scope: {accountId, campaignId?, adGroupId?, targetId?},
  params: {...},                // 算法专属参数（§七）
  criteriaProfileId,            // 条件判据，AND 逻辑，6 运算符 ≥ ≤ > < = between
  limits: {minBid, maxBid, maxChangePercent, daysToObserve},
  window: {daysToAnalyze, daysToIgnore},
  schedule: {cron|hourly, timezone},
  dedupe: stackable | mutuallyExclusive,
  goal,                         // profit|volume|tos_push|clearance|launch（§4.4）
  assignedVia: direct | inheritedFromStrategy
}
CriteriaProfile { id, name, conditions: [{metric, op, value|min|max}] }
Action { kind, entityType, entityId, before, after, reason, calculation[], metricsSnapshot{} }
```

**两条硬规则**（Scale Commander 设计原则，【A】）：
1. **`calculation[]` 是必填字段**（`{step, expression, value}`）。没有算术步骤的候选一律不生成——它是审计、UI 展开、LLM 复核三者共用的证据源。
2. **"the plan a person reviews must be exactly the plan that executes"**：候选生成 = 预览 = 执行输入，同一份数据对象，不做二次计算。preview 不可能与执行漂移。

### 2.2 四层职责划分（07 #10：AI 管 bid，规则管离散事件）

| 层 | 管什么 | 形态 | 学习信号速度 |
|---|---|---|---|
| **L1 事实层** | 指标口径、归因窗口、显著性门槛、响应估计（bid→CPC） | 纯函数，每次现算 | 当天可观测 |
| **L2 动作层** | bid 用公式/算法（连续量）；否词/收割/预算/状态/位次用规则（离散事件） | 确定性 | 3-7 天 |
| **L3 策略层** | 什么时候该用哪类规则、goal 怎么调 | **agent 在此** | 14-30 天 |
| **L4 审批层** | 三道闸 + 快照 + 回滚 + 审计 | 确定性 | — |

**为什么 bid 不能走规则**：规则是"条件→动作"，天然离散；bid 是连续量，规则化后必然出现"ACOS 45.1% 降、44.9% 不降"的锯齿，且降完 CPC 未必降（§4.6 实测 bid↔CPC 无解析关系）。Helium 10 Ads 的做法就是这个分工：**Bid AI 管出价，显式规则管收割/否词/预算**【A】。

### 2.3 策略层（07 #1，v1 完全缺失）

v1 是「规则直接绑对象」，导致同一套阈值在 45 个活动上复制 45 份，改一次要改 45 处。v2 引入：

```
Strategy { id, name, version, effectiveFrom, effectiveTo,
           frequency:{everyNDays, atHour}, excludeDays,
           ruleIds[], goal, objectScope[] }
Rule ←→ Strategy ←→ Object    （多对多）
```

- 策略带**版本号**：每次改动 +1，执行时留存当时规则详情 + 当时广告数据（07 #6）。
- **执行频次与排除窗口在策略层定义**，不在规则层——这样"排除近 2 天"只写一次。
- 同一对象同一类型只能绑 1 个策略（优麦云约束【A】）；不同类型可同时绑（如竞价策略 + 预算策略）。
- **优先级**：定时策略 > 自动化策略 > 卡位策略（优麦云原文【A】）。

## 四、出价算法（L2 连续量层）

### 4.1 三条最优 bid 公式（Scale Insights 官方【A】，Scale Commander 已实现为 `optimumBid()`）

| 场景 | 公式 | 说明 |
|---|---|---|
| 有销售额 | `bid = (销售额 ÷ 点击) × 目标ACOS` | = RPC × 目标ACOS |
| 有售价、有订单 | `bid = 售价 × 目标ACOS × (订单 ÷ 点击)` | = 售价 × 目标ACOS × CVR。例 $20×0.30×0.20 = $1.20 |
| **无销售额（最值钱）** | `bid = 售价 × 目标ACOS ÷ 点击` | 例 $20×0.30=$6 可花 → 10 击 $0.60、12 击 $0.50。**点击累积即自动双曲衰减，无需 step** |

第三条是 IvyeaOps 五杠杆完全没有的，且实现成本极低（一个函数）。**但它有一个前提：CPC ≈ bid。本账户这个前提不成立，见 §4.6。**

### 4.2 花费闸门（反直觉但极正确）

```
若 spend < 售价 × 目标ACOS 且 current_bid < optimum_bid → 跳过（不抬价）
```
含义：还没花到"一个订单的允许成本"，而你的出价已经低于上限，抬价没意义。**这条能消掉大量低点击关键词的无效调整噪声**——本账户 42/81 个零单词合计只花 $766【M】，绝大多数连一个订单的允许成本都没花到。

### 4.3 归一化 + Amazon 物理约束（`effective_bid`）

06 只处理了 placement 加价，**漏了动态竞价 ±100% 的放大**（07 §5 补）。两者叠加时实际 CPC 可达 base bid 的 2×(1+placement%)。

```
effective_bid = base_bid × (1 + placement%) × dynamic_factor
dynamic_factor ∈ [0, 2]   // up&down 所有位次最多 ±100%，默认取 1.0（保守）
```

反解（算目标 bid 时用）：
```
normalized_bid = target_bid × (100 ÷ (100 + placement加价%)) ÷ dynamic_factor
例：TOS 50% → ×100/150=0.67；100% → ×0.86；200% → ×0.57
```

**其他物理约束**（07 §5，全部【A】）：

| 约束 | 数值 | 对引擎的含义 |
|---|---|---|
| 动态竞价 up&down 幅度 | 所有位次最多 ±100% | 算出的"最优 bid"必须 ÷2 再比，否则以为在 target ACOS，实际成交价是 2 倍 |
| 位次加价上限 | 900% | placement 规则 max 夹 0-900 |
| SP 搜索词保留 | 95 天 | 回溯窗口 >95 天拿不到搜索词级数据 |
| SB 搜索词保留 | 60 天 | SB 规则回溯 ≤60 |
| 单次报表跨度 | ≤31 天 | 60 天分析窗必须拆两次拉取 |
| SP 自动活动 | 不能改关键词 bid，只能改投放组 | 先读 `targetingType`（0=手动 1=自动）再决定 op_type |
| bid 地板 | $0.02 | 全局 |

### 4.4 Goal × 盈亏锚点（Teikametrics【A】）

```
ACOS Limit = 广告前毛利率（= 盈亏平衡线）
允许出价 = ACOS Limit × Goal 区间系数
```
| Goal | 区间 | 含义 |
|---|---|---|
| Launch | 100–125% | 新品，允许亏着推换排名 |
| Grow | 95–100% | 保本推 |
| ROAS / Profit | 1–100% | 按利润出价 |
| Liquidate | 100–150% | 清库存，激进 |

IvyeaOps 的 5 模式（§3.2 表）是同一思想的另一套语言，可映射：`profit→ROAS·Profit`、`volume→Grow`、`volume_with_top_of_search_push→Launch+TOS`、`clearance→Liquidate`、`launch→Launch`。

**关键**：goal 挂在 **campaign** 上，不是账户上（07 #8）。整体缩放判据松紧，不换规则。

### 4.5 抑制-试探状态机（Ad Badger，最值钱的非线性机制【A】）

bid 到 min bid 的两个触发：①有单但持续超目标 ACOS ②高点击无单。到地板后：

```
Scenario 1：在 min bid 达成目标 ACOS → 保持运行（理想态）
Scenario 2：仍在 min 表现差 →
    抑制该词一段时间（suppressed_until）
    抑制长短取决于【活动整体健康度】：
        活动优于目标 ACOS → 激进测试模式（对被抑制词反向抬价试探）
        活动超目标 ACOS   → 保守，抑制更久
```

字段：`suppressed_until`、`suppress_count`、`last_probe_at`，需 3-7 天调度器。
**这是唯一能处理"降到地板价仍不赚"的长尾词的机制**——否则只剩一刀切否定。本账户 lat pulldown 三兄弟（559 击 / 3 单 / $473.4【M】）就是典型：不该直接否，该先降到底再抑制。

### 4.6 本账户实测校准（06/07 都没有的一节，v2 核心增量）

#### (a) bid↔CPC 无解析关系 → 公式必须带校准系数

417 条有效记录：`avg_bid $0.899` / `avg_cpc $1.255` / **`cpc÷bid` 均值 1.396、范围 0.496~9.0**【M】。按 bid 分档看比值在 0.96~3.46 之间剧烈波动。

**结论**：CPC 由拍卖竞争度主导，bid 只决定"参与资格"不决定 CPC。所以：

```
bid = 售价 × 目标ACOS ÷ (点击 × CPC_BIAS)     // CPC_BIAS = cpc÷bid 的滚动中位数，本账户初值 1.40
```
`CPC_BIAS` 必须由 L1 层每周重算（按 ad group 分组更准），写死就是 40% 系统性偏差。

#### (b) 阈值不能写死：统计显著性下限

用全店 CVR 1.79% 反算【M】：

| 判定目标 | 所需 clicks（80% 把握） | 90% | 95% |
|---|---|---|---|
| 判定"这词真的不行" | **89** | 127 | 165 |
| 判定"这词明显好"(CVR=2×基准) | 82 | — | — |

而外部默认值是 20-25 clicks。**本账户 81 个词里 clicks≥30 的只有 22 个，≥100 的只有 7 个，≥165 的 0 个**【M】——按 165 击的标准，一个词都判不了。

#### (c) 走前回测：所有阈值方案都误杀 2 单

训练窗 11-01~11-07（1016 clicks / CVR 1.67%），验证窗 11-08~11-15【M】：

| 方案 | 砍掉 | 省下 | 误杀订单 |
|---|---|---|---|
| clicks≥10 且 0 单 | 15 词 | $265.41 | 2 单 |
| clicks≥20（外部默认） | 6 词 | $152.52 | 2 单 |
| clicks≥30（积加默认） | 3 词 | $83.49 | 2 单 |
| clicks≥50 | 1 词 | $11.70 | 0 单 |
| clicks≥100 | 0 词 | $0 | 0 单 |
| 贝叶斯收缩 posterior<盈亏平衡 | 76 词 | $1213.63 | **12 单** |

**"30 击还是 20 击"在本数据量下统计上不可分辨**。贝叶斯方案灾难性，因为全店 CVR 已低于盈亏平衡线——用"低于盈亏平衡就砍"的逻辑，等于把整个账户砍掉。

**v2 的对策**：P0 的否词规则**默认不启用**，改为"只出候选不自动执行"，且判据用**排序而非阈值**：

```
按 CPA 降序（分母加 1 防除零）取 top-N 作为"止血清单"，N 由人工定
实测：top10 花 $531.17 得 7 单 ROAS 1.77 CPA $75.9；全保留 ROAS 1.15
      → 砍到 top10 是本账户当前最优区间
```
排序问题对样本量的要求比"判定单个词好坏"低一个数量级——这是本账户唯一站得住的用法。

#### (d) 目标 ACOS 本身是错的

盈亏平衡 CVR = CPC ÷ (AOV × 目标ACOS)【M】：

| 目标 ACOS | 需要的 CVR | 实际 CVR 1.79% |
|---|---|---|
| 20% | 3.68% | 不达标 |
| 25% | 2.94% | 不达标 |
| **30%** | **2.45%** | 不达标 |
| 35% | 2.10% | 不达标 |

**四个目标档位全不达标**。这不是广告问题，是漏斗/Listing/价格问题（CVR 1.79% × AOV $134.6 × CPC $0.99 = ACOS 41.13%）。
→ 引擎必须有一条规则叫 **"目标不可达告警"**：当 `实际CVR < CPC/(AOV×targetACOS)` 时，**不出任何降 bid 建议，直接报警"该修 Listing 不是修广告"**。这条是外部平台全都没有的（06 §0 已指出）。

#### (e) 自动 vs 手动：结构问题比出价问题大

| 类型 | 活动数 | 花费 | 点击 | 单 | CPA | ROAS |
|---|---|---|---|---|---|---|
| 手动 | 45 | $3145.09 | 2880 | 48 | **$65.52** | 2.33 |
| **自动** | **12** | **$1119.48** | **1411** | **29** | **$38.60** | **2.71** |

自动用 1/3 的钱拿 38% 订单，CPA 便宜 41%【M】。
另有 10 个 ROAS>2 且预算打满的活动被 $5-20 日预算卡住（如 31739234228412 ROAS 9.86 预算 $10、152755922360397 ROAS 11.38 预算 $5）【M】。

**v2 的第一批动作应该是**：把预算从 CPA $91.63 的手动活动（19 个打满、$1374 只 15 单）挪给自动活动和这 10 个高 ROAS 活动——**这是改预算，不是改 bid**。规则引擎的 #8 日预算规则比 #1 bidding 更值钱。

## 五、防错硬约束（全部在 L1/L4，不占规则位）

### 5.1 零值语义保护（07 #2，P0）
销售额与订单量为 0 时，ACOS 与 CPA 也返回 0，"数值虽小但表现不好"【A】。凡是用 ACOS/CPA 做判据的规则，**必须同时加 `订单≥1 或 销售额≥1`**。
本账户实测语义还不一致：campaign 无单时 `acos=0.0`，searchterm 无单时 `acos=null`【M】→ 判无单**只用 `ads_orders` / `clicks`**，不看 acos 字段。

### 5.2 双参数时间窗（06 §9.3）
```
daysToAnalyze：分析窗口（Bidding ≤365，预算 ≤90，默认 7-30）
daysToIgnore ：排除最近 N 天（归因滞后，默认 2，可配 1-7）
daysToObserve：改动后观察 N 天不再动同一对象（默认 7）
```
冷却按**对象**（同一 keyword_id），频率按**账户**（`amazon-ads-diagnostics` 的 72 小时最多一次 bid 变更，比 7 天更细）。
**本账户 bid 14 天从未变动过**【M】——冷却机制现在是空转的，一旦开写就会立刻生效。

### 5.3 阈值现算，不写死（§4.6 的推论）
`min_clicks_for_judgement` 这类参数必须由 L1 层每次重算：
```
min_clicks = ceil( ln(1-confidence) / ln(1-baseline_cvr) )
confidence 默认 0.80，baseline_cvr = 该 ASIN 自身广告 CVR（不是全店）
本账户：0.80 → 89 击；0.90 → 127 击；0.95 → 165 击
```
IvyeaOps 的基准定义值得抄：**CVR 基准 = 该 ASIN 自身广告 CVR（总订单/总点击）**，不是全店、不是全报告平均【A】。

### 5.4 核心词保护（07 #28）
小类目（主导词仅 1-2 个）时，核心大词即使 ACOS 100%+ 也不得降 bid/否词——核心词广告位丢失后自然位 1-2 周跟着塌。正确输出是 `hold_test` + 5 动作（ToS 溢价 +30~100% / Product Pages 归零或负溢价 / 竞价策略改 down only / 单拆 ToS-Only campaign 守位 / 主图改版）。
**红底禁令**（IvyeaOps risk_text.md，【A】）：
- 否核心词同义词（trail cameras/trail cam）→ 切断 A9 相关性
- 一次把 bid 改到 <$2 或当前 −50% 以上 → 立刻掉出首页，回来要 2-3 周
- 改完 5 天内频繁调整 → A9 重新学习，数据归零
- 删核心词 campaign 重建 → 历史清零，只能改不能删

### 5.5 置信度门控（07 #7，比 risk_score<0.5 更实用）
```
low    → 只能 observe / listing_feedback / manual_review
medium → 可 hold_test / reduce_bid
high   → 才能 scale_up / negative_candidate
```
按**动作的不可逆程度**分级，而不是按风险分统一卡 0.5。
另加一条：**7/14/30 天三档结论不一致 → 一律降级为 observe**【A】。

### 5.6 优先级倒挂校验（07 #29）
优先级链：`CTR/CVR 杠杆 > 长尾词辅推 > 出价调整 > 否词`。
若方案里否词排在 CTR/CVR 类之前 → 判定倒挂，打回。

### 5.7 诊断顺序固定（amazon-ads-diagnostics【A】）
`ASIN → Campaign → Ad Group → Target/Keyword → Search Term → Placement`。
顺序错了会把"Listing 转化问题"误判成"出价问题"——本账户正是这种情况（§4.6d）。

## 六、安全写入路径（抄 lingxing_operate.py，938 行【A】）

### 6.1 工单三道闸（顺序执行，任一不过即拒）
1. **三重独立 LLM 复核**：data-rigour / devil's-advocate / business-balance 三个 persona，全部 approve 且最差 risk_score < 0.5；**解析失败 = fail-closed 不通过**。（诚实注记：单 provider 下"独立"=分开调用+对抗性提示词。）
2. **确定性 guardrail**（代码写死，LLM 绕不过去）：
   - `store_scope` 店铺白名单——**白名单为空 = 全部禁止（fail-closed）**
   - `op_type_known` 操作类型必须注册过
   - `change_magnitude` ≤ max_change_pct（默认 20%）
   - `value_positive` / `state_valid`(enabled|paused)
   - `bid_bounds` ∈ [0.02, ceiling]
   - `cooldown` 近 cooldown_days 天不重复操作同一对象
   - **`zero_value_guard`**（v2 新增）ACOS/CPA 类判据必须带订单≥1
   - **`target_reachable`**（v2 新增）目标 ACOS 不可达时禁止出降 bid 建议（§4.6d）
3. **人工最终确认**：工单在 UI 里等人点批准（decided_by 记名）。

### 6.2 回滚机制
- **执行前抓快照**：OP_TYPES 注册表每个写操作声明 snapshot_dataset/id/value，执行前把 live 值存进 `ticket.snapshot_json`【A】。
- **逆序还原**（Scale Commander `rollback(runId)`，【A】）：按 runId 逆序还原每条 before 值，回滚本身再写一条审计；`REVERSIBLE_VALUE_KINDS` 区分"值回写"与"创建类动作（删除）"。
- 工单状态机加 `rolled_back` 终态 + 回滚也走同一审批闸（防回滚本身误操作）。
- D4（Atom11 rollback）核实结论：Atom11 官网/公开文档**未披露任何回滚机制**→ 放弃搬运，D4 关闭，以 IvyeaOps 快照 + Scale Commander 逆序为准。

### 6.3 熔断
写操作连续失败 → circuit breaker：自动 disable operate 总开关 + send_alert 告警，人工排查后才能重开【A】。

### 6.4 Review 模式（06 §9.4，v1 缺失）
除"逐条工单"外，增加**集合批准**：一次接受一批候选（Teikametrics / Scale Insights 均为此形态）。
否则日常运维会被工单淹没——本账户 81 个词，Scale Insights 典型规则（ACOS>45% 降 15%）一次触发 49 个【M】。

### 6.5 限时人工覆盖 + 到期还原（06 §6.6 / 07 #9）
```
工单类型 experiment { target, mode: fixed|multiplier, value, expires_at, auto_revert: true }
```
到期由调度器自动还原并生成审计记录。这是 D4 的**产品化答案**：不是"后悔药"，是"有时限的人工意志"。
与 Ad Badger 的"事件结束自动复位"同构（"no cleanup rules required"）。

### 6.6 执行异常监控（07 #5，v1 只有失败熔断）
每小时检测上一小时策略是否 `未执行 / 一直等待 / 一直在执行中 / 执行失败` → 告警。
**"卡住不动"和"失败"是两回事**，v1 只处理了后者。

### 6.7 策略版本化 + 执行时数据快照（07 #6 / #26，P0）
- 每次改策略 → `version +1`，可回看当时规则详情。
- **执行时留存当时的广告数据**（不只是执行前状态快照）——这是"为什么当时这么调"的唯一证据链，比工单里的 rationale 更硬。
- 与模块2 `op_ticket` 表对接：`proposed→reviewed→guardrailed→approved→executed|rejected|rolled_back`。

### 6.8 OP_TYPES 注册表
```python
OP_TYPES = {
  "campaign_budget": {category:"modify", num_field:"daily_budget",
      snapshot:("sp_campaigns","campaign_id","daily_budget")},
  "keyword_bid":     {snapshot:("sp_keywords","keyword_id","bid")},
  "target_bid":      {snapshot:("sp_targets","target_id","bid")},
  "adgroup_bid":     {snapshot:("sp_adgroups","ad_group_id","default_bid")},
  "placement_modifier": {snapshot:("sp_campaigns","campaign_id","placement_json")},
  "negate_keyword":  {category:"add", ...},
```

## 八、落地清单 v2（按"值钱程度"排序，不按模块顺序）

### 第 2 批：L2 动作层（拿到写权限后）
