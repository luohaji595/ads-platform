# 模块1：数据接入 —— 结论与落地设计（v1）

> 主线文档：02-模块与搬运来源梳理.md 模块1（P0）。本文为模块1执行产出。
> 证据分级：【A】官方文档/开源源码 | 【B】官网帮助/定价页 | 【C】第三方评测 | 【D】待核实
> 逆向说明：本模块取证对象均为公开文档与自有 API 通道，未遇加固/反调试/反抓包/混淆/设备绑定，无需动用 REA。

## 一、结论先行

1. **主通道分读写两条**：**读侧 = 积加 MCP（2026-11-14 实测四张核心表全部取到真实数据，零审批、零配置）**；**写侧 = Amazon Ads API 官方 Reporting/写接口**（个人卖家用 Direct Advertiser 自助表单，审批 ≤1 个工作日，官方未列专业卖家门槛/最低消耗）【A】——待核实清单【D】第 1 条就此关闭（残余风险见 §4）。
2. **四类报表在 v3 全部有官方接口**：搜索词/关键词/投放/广告位/预算各就各位，异步报表机制（创建→轮询→下载 GZIP JSON）【A】。
3. **积加 MCP 已实测取数**（不只是接口地图）：`adsSpCampaigns` / `spKeywordsPage` / `spSearchKeywordsReport` / `adsSpPlacement` 四张表返回真实数据，且自带 `bid`（当前出价）、`bidStrategy`（竞价策略）、`placement`（广告位）三个关键字段【A-实测，2026-11-14】。受 60s/次 节流约束。**但广告类接口全部只读，无写能力。**
4. **数据时效与回溯窗**：SP 搜索词数据保留 95 天、SB 60 天，单次报表最长 31 天区间【A】→ 本地库必须做"滚动快照"，错过 95 天即永久缺失。
5. 建议形态：**读侧今天就能跑（积加→SQLite 指标快照→规则引擎出建议单）**；写侧等 Ads API 批准后接执行层；后台手工导出为最后兜底。

## 二、主通道：Amazon Ads API Reporting v3

### 2.1 准入（Onboarding 三步）【A】

来源：Amazon Ads API 官方 Onboarding 文档
（[overview](https://raw.githubusercontent.com/idealerror/amazon-ads-api-docs/main/en-us/guides/onboarding/overview.md) /
[apply-for-access](https://raw.githubusercontent.com/idealerror/amazon-ads-api-docs/main/en-us/guides/onboarding/apply-for-access.md)，镜像自官方站）。

1. **创建 Login with Amazon (LwA) 应用**：免费、免审，作为 API 客户端凭证。
2. **申请 API 权限**：两类身份——Partner（给他人做工具的，走 [Amazon Ads Partner Network](https://advertising.amazon.com/partners/network)）；**Direct Advertiser（自己广告自己用，走自助表单，直接入口：`advertising.amazon.com/partner-network/register-api` → 选 Direct Advertiser）**。表单含用途说明 + License Agreement + Data Protection Policy。审批 ≤1 个工作日，邮件通知。
3. **把 API 权限绑定到 LwA 应用**：⚠️ **开发者账号与 Ads API 权限的绑定一经设定不可更改**（官方原话 "cannot be changed once it is set"），务必用团队主邮箱操作。

结论：个人自用工具 = Direct Advertiser 路径，无需 Partner 注册。官方文档未要求专业卖家账号或最低广告消耗【A】。

### 2.2 异步报表机制【A】

```
POST https://advertising.amazon.com/reporting/reports
  Content-Type: vnd.createasyncreportrequest.v3+json
  Headers: Amazon-Advertising-API-ClientId / -Scope / Authorization: Bearer
→ 返回 reportId → 轮询状态 → COMPLETED 后下载 url（GZIP_JSON）→ 解压入库
```

### 2.3 四类报表 → reportTypeId 映射【A】

| 我们要的报表 | reportTypeId | adProduct | 关键配置 | 保留期/区间 |
|---|---|---|---|---|
| 搜索词报表 | `spSearchTerm` / `sbSearchTerm` | SPONSORED_PRODUCTS / _BRANDS | `groupBy:["searchTerm"]`，`timeUnit: DAILY`；`keywordType` 过滤器区分关键词(BROAD/PHRASE/EXACT)与投放表达式(TARGETING_EXPRESSION*) | SP 95 天 / SB 60 天；单次 ≤31 天 |
| 关键词/投放报表 | `spTargeting`（overview 表列 Targeting：SP/SB/SD/ST 均有） | SPONSORED_PRODUCTS | groupBy targeting 维度 | 同上量级（细节按 report-types/targeting 页核对，标注【D-细节】） |
| 广告位报表 | SP：**campaign 报表 + `groupBy:["campaignPlacement"]`**（SP 无独立 placement 报表，官方明示）；SB：`sbCampaignPlacement`（preview） | SPONSORED_PRODUCTS / _BRANDS | columns 加 `placementClassification` | SB 60 天 |
| 预算/活动报表 | `campaign`（SP/SB/SD 通用） | 各 adProduct | columns 含 `campaignBudgetAmount` / `campaignBudgetType` / `campaignBudgetCurrencyCode` / `campaignStatus`；`timeUnit: DAILY` 可做预算日消耗节奏 | 单次 ≤31 天 |

关键口径注意（搜索词报表）【A】：
- 只含"至少产生 1 次点击的展示"；无搜索词的展示（商品页 placement）搜索词列为 `*`。
- 归因列用 `purchases7d / sales7d`（另 1d/14d/30d 全套）；ACOS 取 `acosClicks7d`。
- SB 报表目前 preview：`isMultiAdGroupsEnabled=False` 的 SB 活动数据缺失。

核心列最小集（搜索词表为例，直接抄官方样例）：
`impressions, clicks, cost, campaignId, campaignName, campaignBudgetAmount, campaignStatus, adGroupId, adGroupName, date, keywordId, keyword, matchType, keywordType, targeting, searchTerm, keywordBid, purchases7d, sales7d, acosClicks7d`

## 三之二、积加 MCP 实测取数（2026-11-14，E1 读侧已跑通）【A-实测】

> 用户提示"Amazon Ads API Onboarding 可以用本机积加的 MCP"。实测结论：**读侧完全可用，且比自建 API 更快上手；写侧没有，仍需 Ads API。**

### 3.2.1 授权与调用

- `jijia_get_auth_status` → `keychain: present`，token 已存在，**零配置**。MCP 工具名 `mcp__jijia__jijia_call`。
- 必填参数（踩过的坑，直接抄）：
  - 广告类接口：`marketId` + `count` + 时间范围 `startDate`/`endDate`（缺一个就报 `必填参数[marketId，count]不能为空` / `请求时间范围不能为空`）
  - 店铺列表 `/middle/base/market/page`：`page` + **`pagesize`（全小写，不是 pageSize）**
- `marketId` 获取：`/middle/base/market/page` 返回 `data.rows[].marketListVos[]`，每条含 `marketId` / `market`（如 `amazon-us`）/ `countryName` / **`adsState`**（`Successfully` = 广告授权正常）/ `authExpireDate`。本账号实测 3 个 market：`7=amazon-us`、`12=amazon-us`、`8=amazon-es`，`total=18`。
- 节流：仍受 60s/次 约束，本会话按 sleep 45~60 串行调用，无报错。

### 3.2.2 四张核心表实测字段（真实数据，非文档抄录）

| 接口 | 实测返回字段（关键项） |
|---|---|
| `adsSpCampaigns/query` | campaignId / campaignName / **cost / clicks / impressions / ctr / cpc / cvr** / adsSales / otherProductSales / adsOrders / adsProductOrders / **acos / roas / cpa** / **dailyBudget** / portfolioId+portfolioName / targetingType / servingStatus / startDate / state / id（行 id）/ hash |
| `spKeywordsPage/query` | 上表指标 + **keywordId / keywordText / matchType / groupId+groupName / `bid`（当前出价）** |
| `spSearchKeywordsReport/page` | 上表指标 + **`query`（用户真实搜索词）** / keywordText / matchType（0=EXACT、1=PHRASE、2=BROAD，实测样本推断，待官方确认） |
| `adsSpPlacement/page` | 上表指标 + **`placement`（如 `Detail Page on-Amazon`）/ `bidAdjustment` / `bidAdjustmentName`（如 "0%"）/ `bidStrategy` + `bidStrategyName`（如 "固定竞价"）** |

三个可直接落地的发现：

1. **`bid` 字段直接给当前出价** —— 改 bid 规则（new_bid = RPC × target）不需要额外查一次关键词配置，同一张表就能算。
2. **`bidStrategy` 直接给竞价策略（只在 placement 接口有）** —— 这正是 `effective_bid = base_bid × (1+placement%) × dynamic_factor` 里 `dynamic_factor` 的来源（07 文档 §5 那条公式现在有数据源了）。⚠️ **campaign 接口的行里没有 bidStrategy 字段**，别在 campaign 表上找。
3. **零值语义按接口不一致**（实测 45 行 campaign：orders=0 的 40 行全部 `acos=0.0`，0 行 null）：
   - `adsSpCampaigns`：无单 → `acos=0.0`、`roas=0.0`（**0 不是 null**）
   - `spSearchKeywordsReport`：无单 → `acos=null`
   → **判"无单"一律用 `ads_orders=0` 或 `clicks`，不要靠 acos 是否为空/是否等于 0。**（优麦云是"ACOS/CPA 返回 0"的口径，同样必须加"订单≥1"闸门。）


### 3.2.3 数据粒度与取数陷阱

- **行粒度 = 日 × 实体**：同一 campaignId 在 11-01～11-05 返回 5 行，`createDate` 实为**报表日期**（不是活动创建日），`startDate` 才是活动真实开始日。入库主键必须用 `createDate`。
- **默认按 `id` 升序分页**：`page=1,count=10` 拿到的是最早的 10 行（2 个 campaign × 5 天），不是最新。**拉当日数据必须用日期窗口限定**（见下条 `endDate` 排他上界），否则会误判"数据滞后"。
- **⚠️ `endDate` 是排他上界（exclusive），这是最容易静默丢数据的一条**（2026-11-14 实测矩阵，四个接口一致）：

  | 传参 | 实际返回 |
  |---|---|
  | `(D, D)` | D 为最新一天时返回 **0 行**（searchterm 例外，正常返回 D 当天） |
  | `(D, D+1)` | **正好返回 D 当天**（campaign 46 / keyword 64 / searchterm 68 / placement 118） |
  | `(D-1, D)` | 只返回 D-1 当天 |
  | `(D-1, D+1)` | 返回 D-1 与 D 两天 |
  | `(11-10, 11-14)` | 返回 11-10..11-13 四天共 188 行 |

  → **拉 D 当天必须传 `startDate=D, endDate=D+1`**。用 `(D,D)` 会静默丢掉最新一天（表现为"11-13 没有数据"，实际数据存在）。
- **数据 T+1 才可用**：今天（11-14）查 `(11-14, 11-15)` 拿到的是 11-13 的数据；当天数据当天不可得。
- `hash` 字段是行级指纹，可直接用作幂等 upsert 的去重键（比自建 (date, campaignId, keywordId…) 复合键更省事，但跨库不可移植，建议两者都存）。
- **⚠️ 分页参数是假的（2026-11-14 实测，最关键的一条）**：四个广告接口**全部忽略 `page`**——`page=1/2`、`pageNum=2`、`pageIndex=2`、`offset=200` 返回的首尾 id 完全相同（campaign 实测 first=5736218 last=5736619，日期都是 2026-11-01..11-04）。**没有任何可用的翻页手段。**
- **⚠️ `count` 有硬上限**：campaign `count=500` 正常返回 500 行、`count=1000` 报 `code=40004` 返回 0 行；placement `count=200/500` 都返回当日全量、`count=999` 报 `code=50099`。→ **安全值 500，且不能指望靠加大 count 拿全区间。**
- **⇒ 结论：只能"一天一查"**。13 天区间一次查会被 500 行上限截断（实测 11-01～11-13 只回来 11-01..11-09 的 500 行），必须把日期区间切成逐日单查。代价是调用数 = 天数 × 数据集数，按 60s 节流 13 天 ×4 数据集 ≈ 52 分钟；日常增量只有 4 次调用。
- **零值语义按接口不一致**：`adsSpCampaigns` 无单时 `acos=0.0`/`roas=0.0`；`spSearchKeywordsReport` 无单时 `acos=null`。**判"无单"一律用 `ads_orders=0` 或 `clicks`**，不要靠 acos 是否为空/是否等于 0。
- `targetingType` 实测 0=手动、1=自动（campaign 名含"自动"者为 1，推断，未获官方枚举）；`state` 实测恒为 0，含义未知，**启停判断用 `servingStatus`**（实测有 `CAMPAIGN_STATUS_ENABLED`、`CAMPAIGN_OUT_OF_BUDGET`）。
- **必须直连**：积加白名单校验请求出口 IP，走代理（Clash 等）会鉴权失败。
- 报表可回溯起点：`dim_market` 元数据 `AdsReportInitDateBegin=2025-10-31`、`AdsReportPeriod=5`（本账号）。

### 3.2.4 写侧：没有

`jijia_list_endpoints` 全量筛查：广告类 18 个接口**全部是 `query` / `page` 只读**；`修改` 关键字只命中商品资料/品类/汇率三个非广告接口。**结论：积加 MCP 只能做 E1 读，改 bid / 改预算 / 加否词必须走 Amazon Ads API 写权限。**

→ 这直接决定架构：**读侧立刻可用（今天就能跑规则引擎出建议单），写侧仍卡 Onboarding**。模块3 的"执行"必须等 Ads API 批准；在那之前平台是"只出建议、人工执行"模式。

## 四、残余风险与待办

1. 【D-残余】Direct Advertiser 申请的**审批结果个案性**：官方未写门槛但保留拒审权；若被拒，**读侧不受影响**（积加 MCP 已跑通），只有写侧会卡住，退路=人工执行建议单 + 后台批量表。
2. 【D-细节】`spTargeting` 报表的具体 columns/groupBy 待按官方 report-types/targeting 页补（不影响架构，晚点核对）。
3. API 配额（rate limits）数值待拿到开发者账号后在 console 看【D】。
4. 【D-待确认】积加 `matchType` 枚举 0/1/2 与 EXACT/PHRASE/BROAD 的对应关系为实测样本推断，需官方文档或再取几组样本确认——**错一位就会把精准词当广泛词处理**。
5. **行动项（已修订）**：
   - ~~立即走 Onboarding 三步~~ → **降级**：不再阻塞读侧。
   - **立即可做**：用积加 MCP 落第一版日快照（marketId 7 / 2026-11-01 起），验证入库与幂等。
   - **写侧前置**：仍建议尽早用主邮箱走 LwA → Direct Advertiser → 绑定（绑定不可改），因为写能力是平台从"建议"升级为"执行"的唯一路径。

## 五、落地设计：每日摄取管道（模块1 → 模块2 的接口）

```
每日 06:10 本地任务（launchd: com.baoyanan.ads-ingest）
 ├─ A主通道（读）：积加开放平台 REST —— 已实现，代码在 ingest/
 │   0) /middle/base/market/page 取 marketId（pagesize 全小写；adsState 必须=Successfully）
 │   1) adsSpCampaigns/query         逐日（含 dailyBudget / targetingType / servingStatus）
 │   2) spKeywordsPage/query         逐日（含 bid 当前出价 / matchType）
 │   3) spSearchKeywordsReport/page  逐日（query=真实搜索词）
 │   4) adsSpPlacement/page          逐日（placement / bidAdjustment / bidStrategy）
 │   调用间 sleep 60s；startDate=endDate=当日，逐日切分（接口不支持翻页，count 上限 500）
 ├─ B写通道：Ads API（Onboarding 批准后启用）—— 改 bid/预算/否词
 ├─ C备份：Ads API 读 或 后台 CSV 放 inbox/
 └─ 入库：SQLite（ingest/data/ads.sqlite3）
      dim_market + fact_campaign_daily / fact_keyword_daily / fact_search_term_daily / fact_placement_daily
      幂等 upsert（业务主键 + row_hash 双保险）；source 标记来源；run_log 记录每次运行（区间/页数/行数/状态/note）
```

- 95/60 天保留窗 → 错过即失，管道停跑 >N 天要在预警里报警（联动模块6）。
- 本地表结构细节归模块2（IvyeaOps 参照），此处只定接口：**摄取层输出=统一宽表行**。
- 已落地代码：`ingest/jijia_client.py`（REST 客户端，钥匙串取凭证 + MD5 签名 + 强制直连 + 60s 节流）、
  `ingest/schema.sql`、`ingest/ingest.py`（数据集注册表 + 逐日拉取 + upsert + 报告）、
  `ingest/launchd/com.baoyanan.ads-ingest.plist`（每天 06:10 拉昨日）。
