# 08 · 积加广告自动化能力拆解（"广告 agent"到底是什么）

> 调查方式：只读公开帮助中心 `help.jijiaerp.com`（Helplook 站，正文在 `__NUXT_DATA__` 里）+ **1 次只读 OpenAPI 查询**（`/operation/ads/strategyTemplate/page`）。
> 未登录积加后台、未探测越权接口、未做高频请求。全部结论可回溯到文档 slug 或接口返回原文。

---

## 一、结论先行

1. **积加没有单一的"广告 agent"。** 叫得上 agent 的有两套完全不同的东西：**广告自动化**（规则引擎，真的改 bid/预算/否词）和**积加AI**（数字员工，只出报告不改价）。
2. **真正动出价的是三套规则**。官方术语表把**自动策略 + 分时策略**定义为"广告自动化"，原话："相对于分时策略主要按时间进行自动调整，自动策略是按照表现进行自动调整。**这两者合称为广告自动化。**"第三套是**广告抢位**（按排名触发），官方不把它算进"广告自动化"，但它是三者中**优先级最高**的。
3. **三套规则的执行频率完全不同**：自动策略可配"每 N 天执行一次"+ 冷却；分时策略**每 2 小时**判断一次、整点生效；广告抢位**每小时**跟一次排名。这是三套独立调度器，不是一套。
4. **积加AI 不是执行器。** 官方三个场景里，广告日常监控被明确标为"**场景3（内测中）**"，走"数字员工 + 长期任务 + 技能"路线，产出是报告/建议，**没有任何改 bid 的能力**。
5. **OpenAPI 里几乎没有自动化配置面。** 25 个广告接口全是查询；唯一沾"策略"的是 `strategyTemplate/page`（只能读分时策略模板）。**自动策略和广告抢位在 API 里完全不存在** → 自建平台无法接管积加的规则，必须自己实现规则引擎。
6. **第二条取数路径：官方「MCP套餐」。** 积加AI 营销页明说 MCP 套餐"仅 MCP 数据接口能力，适合自研智能体的技术团队"，可把 ERP 数据封装成 MCP 给外部 AI 读。这是我们平台除 OpenAPI 外的备选取数通道（待评估配额与字段范围）。
7. **本账号实测：唯一的自动化配置是一个 0 应用对象的空模板。** `templateName="分时"`、`strategyType=timeSharingBudget`、`useNum=0`、`status=1`、创建人 洪家洛、创建 2026-08-27、更新 2026-09-07。即积加侧实际上**没有在跑任何自动调节**。

## 二、三层架构（必须分清，否则会买错/用错）

```
┌─ ① 执行层（真的改亚马逊后台的 bid / 预算 / 否词）
│   ├─ 自动策略   YUshRDjG   按"表现"触发   调度：每 N 天 + per-object 冷却
│   ├─ 分时策略   TI32Pt86   按"时间"触发   调度：每 2 小时判断、整点生效
│   │   └─ 官方术语：上面两个合称「广告自动化」
│   └─ 广告抢位   6BEKoDwx   按"排名"触发   调度：每小时跟踪
│       └─ 不在"广告自动化"术语内，但优先级最高，运行时其他规则全部失效
│
├─ ② 积加AI（Agent 层，aiagent.app.gerpgo.com）
│   └─ 智能对话 / 技能中心 / 长期任务 / 数字员工 / MCP市场 / 技能创作中心
│       定位：按 SOP 定时产出报告；广告监控=场景3 内测中；**不执行改价**
│
└─ ③ OpenAPI（取数层）
    └─ 25 个广告接口全为 query/page（零写接口）；策略侧只有 strategyTemplate/page（只读分时策略）
```

## 三、自动策略（按表现触发）— 文档 `YUshRDjG`

### 3.1 术语（官方严格区分，容易误读）

| 术语 | 含义 |
|---|---|
| 自动策略 | 可重复应用的规则组 |
| 应用对象 | 策略挂到哪个广告活动 / 广告组 |
| 优化对象 | 最终被改的那个东西（活动/关键词/商品投放/投放组/受众/搜索词） |
| 应用 / 执行 / 优化 | **三个不同动作**：应用=挂上去；执行=跑了一遍；优化=真的改了东西。冷却只认"优化" |

### 3.2 优化对象 × 可执行操作（括号内为执行顺序）

| 优化对象 | 操作（按优先级） | 适用广告类型 |
|---|---|---|
| 广告活动 | 暂停活动 → 开启活动 → 调整SP竞价策略 → 调整首页首位广告位竞价 → 调整详情页广告位竞价 → 降低预算 → 提高预算 | SP / SB / SD |
| 关键词投放 | 暂停投放 → 开启投放 → 降低竞价 → 提高竞价 | SP / SB |
| 商品投放 | 暂停投放 → 开启投放 → 降低竞价 → 提高竞价 | SP / SB / SD |
| 投放组 | 同上四种 | **仅 SP** |
| 受众投放 | 同上四种 | **仅 SD** |
| 搜索词-ASIN | 添加到否定投放 → 添加到投放 | **仅 SP** |
| 搜索词-关键词 | 添加到否定投放 → 添加到投放 | SP / SB |

> 竞价策略与广告位竞价这两个动作**只对 SP 开放**，且只能挂在"广告活动"这个优化对象上——这和 Amazon 的 API 结构一致（bidStrategy / placement 是 campaign 级字段）。

### 3.3 应用对象 → 可挂的优化对象（关键组合）

| 应用对象 | 可挂优化对象 |
|---|---|
| SP 手动活动 | 活动 / 关键词 / 商品投放 / 搜索词-ASIN / 搜索词-关键词 |
| SP 自动活动 | 活动 / 投放组 / 搜索词-ASIN / 搜索词-关键词 |
| SB 活动 | 活动 / 关键词 / 商品投放 / 搜索词-关键词 |
| SD 受众活动 | 活动 / 受众投放 |
| SD 商品活动 | 活动 / 商品投放 |

> **陷阱**：SP **自动**活动里没有"关键词"这个优化对象，只能改"投放组"。自建引擎如果按 campaign targetingType 一刀切，会给自动活动生成改关键词 bid 的建议单，而这类建议在积加里根本发不出去。

### 3.4 数量限制（设计容量上限时的硬约束）

| 项 | 上限 |
|---|---|
| 单策略应用对象 | 200（所有店铺站点汇总 ≤200） |
| 单次操作 应用对象 × 策略数 | 2000 |
| 单应用对象优化对象 | 2000 |
| 一个对象可挂策略数 | 10（**只算直接应用**，间接作用不计） |
| 一个策略规则数 | 10 |
| 一条规则"或"条件数 | 10 |
| 一个"或"条件内"且"条件数 | 10 |

### 3.5 数据范围（三选一，这是我们最该抄的设计）

| 模式 | 定义 | 参数约束 |
|---|---|---|
| **周期** | 前 N 天 到 前 M 天 | N,M ≥1 且 0 ≤ N-M < 32 |
| **累计** | 从上次优化后 到 前 M 天；起点=策略应用前 N 天 | N≤90、M≤90、N-M≥0 |
| **当日** | 执行当日 0 点 至 执行点 | — |

> "前 M 天"这个 M 就是**归因滞后窗口**——把最近 M 天排除掉，避免拿没归因完的数据做决策。这正是 07 文档里"排除近 1-7 天归因窗口（默认2天）"的产品化实现。

### 3.6 冷却：两次优化的最小时间间隔

- 起算点：**上次执行且实际做了至少一项优化**（不是"上次执行"）。
- 官方例子：策略每 1 天执行一次、最小间隔 3 天 → 7月1日对"广告活动1"做过优化，则之后 3 天该策略对活动1**不再做任何优化**，即使条件满足。
- **与我们 05 文档的 `cooldown 7天` 是同一机制**，只是积加把它做成 per-object 粒度，而不是全局。

### 3.7 移词映射（收割的另一种做法）

把源广告组的搜索词在目标广告组快速建投放；一个源可映射多个目标；竞价在**策略配置时**指定（固定竞价 或 基于平均 CPC 调整）；目标组已存在同投放则**忽略不改**。

> 注意：这是"建投放"，不是"改 bid"。我们的"收割"杠杆（advisory 升 EXACT + bid=RPC×target + 原活动否定毕业）比它多两步：算价 + 否定毕业。

### 3.8 配置三步

1. **选优化对象**（先定"要改什么"）
2. **创建/编辑策略**：条件（或/且嵌套）+ 动作 + 数据范围 + 最小时间间隔
3. **应用策略**：选应用对象（活动/广告组），挂上去

> 系统有**预置策略模板**，可直接用、可增删改（文档只有截图，模板名不可读）。

## 四、分时策略（按时间触发）— 文档 `TI32Pt86`

### 4.1 六类模板

| 类型 | 说明 | 限制 |
|---|---|---|
| 分时调预算 | 按时段调每日预算 | 只支持"每日预算"；生命周期预算（总预算）的 SB 活动不支持 |
| 分时调竞价 | 按时段调 bid | — |
| 分时启停 | 按时段开/停广告 | 官方警告："暂停广告可能对广告质量分有影响，请谨慎使用" |
| 分时调广告位 | 按时段调广告位加价 | **仅 SP** |
| 分时调广告组合预算 | 按广告组合调 | — |
| 分时调 SP 预算上限 | 调 SP 预算上限 | — |

### 4.2 调预算的三种配置方式

1. **按时间**：每天一致（`adjustFrequency=0`）或每周区分（工作日/休息日不同）
2. **按固定值调整**：每时段设"按金额增加 / 按百分比增加 / 直接调整至"；未设时段恢复基准
3. **按比例分配**：每时段占每日预算的百分比；当天所有时段都要设、不可重叠、合计 ≤100%

**按比例分配是累加不是覆盖**（官方例子）：
```
基准 100
00:00-05:00  20% → 预算 = 100×20% = 20      （0点设为 20）
05:00-20:00  50% → 在 20 基础上追加 50 = 70  （5点设为 70）
20:00-24:00  25% → 在 70 基础上追加 25 = 95  （20点设为 95）
```

### 4.3 预算上下限截断

```
基础 1，按金额 +0.5，上限 1.8 → 1+0.5=1.5（≤1.8）→ 取 1.5
基础 1，按金额 +0.5，上限 1.4 → 1+0.5=1.5（>1.4）→ 取 1.4
基础 1，按百分比 +50%，上限 1.8 → 1+0.5=1.5 → 取 1.5
基础 1，直接调整至 2 → 取 2
```

### 4.4 原始基准三选一（决定手动干预的后果）

| 基准模式 | 语义 | 手动改价后 |
|---|---|---|
| 自定义原始预算 | 用户写死的基准 | 手动改动只在**本时段**有效，下次执行被覆盖 |
| 应用策略时的广告预算 | 取应用那一刻各活动当前每日预算 | 同上 |
| **每次执行时取亚马逊后台最新预算** | 执行前 10 分钟自动去亚马逊拉最新值 | 手动改过 → **把原始基准改成手动值**，后续按新基准算 |

> 这是最容易踩的坑：同一句"手动改了价格会怎样"，答案取决于基准模式，两种模式的行为**完全相反**。

### 4.5 执行节奏

- **每 2 小时判断一次**（不是每小时、不是实时）
- 新策略按**整点**生效；规则改动在下一个 **整点 / 整点20分 / 整点40分** 生效
- 只有"自己及上级（活动、广告组）都为开启状态"的分时策略才执行

### 4.6 限制清单

- 同一广告对象，**同类分时策略只能挂一个**（一个活动只能有一个"分时调预算"）
- 国家创建后**不可改**，只能在该国广告用（防币种错配）
- 新旧策略模板**不能并存**：建新会自动关旧；但**建旧不会判断新 → 会同时执行**
- 移除/关闭模板时会弹窗问"还原到原始预算"还是"保持当前"

## 五、广告抢位（按排名触发）— 文档 `6BEKoDwx`

| 项 | 规则 |
|---|---|
| 定义 | SP 广告下对投放中的关键词设目标广告位 + 自动调竞价规则 |
| **优先级** | **最高**。"抢位规则优先于分时策略等其他自动规则"——抢位规则运行期间（**含暂停时段和非抢位时段**）其他自动规则全部失效 |
| 生效延迟 | 抢位规则归档后分时策略立即生效，但需等**下一个小时**才能重新生效 |
| 调度 | **每小时**跟踪一次抢位关键词排名 |
| 成功判定 | 广告排名 **达到或高于** 目标位即算成功 |
| 失败动作 | 按设定幅度，在"**发起抢位时间点的实际出价**"基础上上浮（不是按当前出价滚雪球） |
| 唯一性 | 同一广告组下同一词同一匹配类型，只能有一个生效抢位规则 |
| 支持范围 | **仅 SP-商品广告-关键词投放-精准匹配**（历史遗留的其他匹配类型，系统按词本身去前台搜排名，等价精准） |
| 额度 | 开启和**暂停**都占额度；**归档不占**；超额度需额外购买 |
| 判断方式 | **ADID 更精准**（同店同 ASIN 在多个 SP 关键词活动里 ADID 不同）；用 ASIN 只要该 ASIN 广告出现在该位就算命中，无法区分来自哪个活动 |
| ADID 获取 | 需用积加浏览器插件从亚马逊广告后台提取，格式不对会阻断提交 |

**排障要点（官方 QA #9）**：某活动设了分时策略却不执行 → 先去广告抢位看该活动下有没有关键词加了抢位任务。**不管任务是启用还是暂停**，都会让该关键词所属活动**不执行任何分时策略**。

## 七、本账号实测（唯一一次 API 调用）

```
POST /operation/ads/strategyTemplate/page
{"marketId":7,"page":1,"pagesize":50}
→ total=1
```

| 字段 | 值 | 解读 |
|---|---|---|
| templateName | 分时 | 名字是默认的，不是业务命名 |
| strategyRules / strategyType | 分时调整预算 / `timeSharingBudget` | 六类里的第一类 |
| countryNames / currency | 美国 / USD | — |
| **useNum** | **0** | **应用对象 0 个 → 模板存在但没挂任何广告活动，等于没生效** |
| status | 1 | 启用 |
| createUserName | 洪家洛 | 不是我建的 |
| createTime / updateTime | 2026-08-27 / 2026-09-07 | 建完就没再动 |
| basicValue | 40 | 基础预算 $40 |
| isSetBasicValue | 0 | 原始预算非自定义（走"应用时预算"或"每次取后台最新"） |
| templateExpression | 见下 | 完整配置 JSON |

```json
{"isSetBasicValue":0,"adjustingWay":0,"configType":"fixed",
 "timeExpression":{"rules":[{"date":0,"frequencies":[
    {"adjustmentType":"adjustDirectlyTo","endHour":6,"startHour":0,"value":15},
    {"adjustmentType":"adjustDirectlyTo","endHour":24,"startHour":6,"value":40}]}],
  "adjustFrequency":0,"autoParse":1,"displayMode":1,"dateList":[0]},
 "basicValue":40}
```

解读：**每天（`adjustFrequency=0`, `date=0`）**，**0-6 点预算直接调至 $15，6-24 点调至 $40**，固定值方式（`configType=fixed`），基础预算 $40。

> 这个 `templateExpression` 结构可以直接作为我们规则引擎的**序列化参考**——它是产品化的、经过真实账号验证的 schema。

**接口契约补充**：`strategyTemplate/page` 用 `page` + `pagesize`（全小写），**不认 `count`**（传 count 报 `40007 必填参数[page，pagesize]不能为空`）。与 `/middle/base/market/page` 一致。

## 七点五、两个容易混淆的"自动调节"（否定证据）

| 名称 | 实际是什么 | 与广告的关系 |
|---|---|---|
| **智能调价 / 调价助手**（工具 >> 亚马逊 >> 调价助手） | **商品售价**自动调整：跟卖调价（全部跟卖取最低 / 指定卖家 / 排除卖家，竞价对象可选最低卖家或购物车卖家）、库存阈值调价、销量阈值调价 | **与广告 bid 无关**，是 Listing 价格，不是竞价 |
| **自动规则**（G0mdceqp） | **客服工单**自动打标签/改工单状态（沟通渠道、买家消息来源、规则组条件） | **完全无关** |

> 这两项在积加后台都叫"自动"，但都不是广告自动化。查资料时极易误配。

## 八、对我们平台（模块3）的启示

### 8.1 可以直接抄的

| 积加设计 | 为什么值得抄 |
|---|---|
| **数据范围三选一（周期/累计/当日）+ 前 M 天** | 把"归因滞后窗口"做成一等公民，比我们 05 里写死的"丢弃最近 2 天"更灵活 |
| **冷却按 per-object 粒度 + 只在"真优化"时起算** | 比全局 cooldown 更准；避免"执行了但没改"也占冷却 |
| **动作优先级固定顺序** | 我们 05 已有（否词>收割>降bid>加bid>加预算），积加是同思路的另一种排序 |
| **抢位 > 其他规则**的硬优先级 | 排名卡位是"目的性最强"的动作，被其他规则改 bid 会破坏卡位；我们 07 的规则17/18 需要这个互斥 |
| **`templateExpression` 序列化结构** | 产品验证过的 JSON schema，可直接借鉴字段命名 |
| **基准三选一 + 明确的手动干预语义** | 这是"人工改了价格系统怎么办"的唯一正确答案形态，我们 05 完全没写 |

### 8.2 不能抄 / 必须自己实现的

| 项 | 原因 |
|---|---|
| 自动策略 / 抢位的配置读写 | **OpenAPI 完全没有**，积加不给接口 |
| AI 直接改价 | 积加自己也没有（场景3 内测，只出报告） |
| 三重 LLM 复核 | 积加没有这层；这是我们 05 的差异化（也是成本项，个人版建议先关） |
| snapshot 回滚 | 积加有"还原到原始预算"但粒度粗；我们的 `op_ticket.snapshot_json` 更细 |

### 8.3 三条新的实现约束（来自本次调查）

1. **SP 自动活动不能改关键词 bid**，只能改投放组 → 规则引擎必须先读 `targetingType` 再决定出哪类建议单。
2. **分时策略每 2 小时才判断一次**，所以"预算剩余预警"必须按 ≥2 小时的量预留（积加官方建议"可用预算低于 20%/30% 时再提高"）。我们若做分时预算规则，阈值不能设太紧。
3. **抢位与分时/自动策略互斥**（积加是硬失效）。我们若实现排名卡位，必须有互斥开关，否则两条规则会互相打架。
