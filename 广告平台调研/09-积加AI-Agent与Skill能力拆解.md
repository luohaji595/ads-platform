# 积加AI（Agent 层）能力拆解 —— Agent / Skill / Tools 三层与长期任务机制

> 调查日期：2026-11-14
> 调查方式：**匿名静态分析**。只读取公开前端资源（`aiagent.app.gerpgo.com` 的 JS bundle）与公开帮助文档（`help.jijiaerp.com` / `api.helplook.net`），**未登录、未使用 YG 的积加账号、未调用积加 MCP、未做任何鉴权探测**。
> 证据等级：【A】官方文档原文 / 官方截图；【B】前端 bundle 反推的代码事实；【C】推断。

---

## 一、结论先行

1. **积加AI 不是"一个会调价的 agent"，而是一个"技能编排平台"**。它的能力不是写死在代码里的，而是四层拼装出来的：**MCP Tools（数据与动作）→ Skill（约束 SOP 的 SKILL.md）→ 数字员工 Agent（技能组合体）→ 长期任务（定时触发器）**。这四层里，**只有 Tools 层碰得到真实数据，上面三层全是提示词与调度**。【A】

2. **它的 Skill 就是 Anthropic SKILL.md 规范**，带 YAML frontmatter（`name` / `description` / `tools`）+ 正文 SOP。前端把表单字段拼成这个格式再提交，说明服务端消费的就是标准 SKILL.md。【B，代码级证据见 §3.1】

3. **官方只有 7 个技能**（Amazon评论分析×2、意图分析、Amazon商品诊断、Amazon经营月报、Amazon销量预测、效果分析优化），**全部归"产品运营"类**，**没有一个是"改 bid / 加否词 / 调预算"的执行型技能**。7 个全是"分析→建议"。【A，技能中心截图】

4. **官方只有 3 个数字员工**（通用商品优化、优化效果分析、商品优化），工作处理时间 30 天、任务处理时间 7 天、绑定 `统计分析` + `Amazon商品诊断` 两个技能。【A，数字员工列表截图】

5. **长期任务当前是"阶段1 半智能"**：AI 出建议 → 真人判断 → **真人执行**。官方把"阶段3 全智能（AI 自判自执行）"写成未来路线图，**明确不是现状**。【A，长期任务文档原文】

6. **能力底座是 19 个 MCP server**，其中积加自有 15 个（`gerp-*`）+ 三方 4 个（卖家精灵 / SIF / Sorftime / 西柚洞察）。广告相关的只有两个：`gerp-ads`（21 tools）与 `gerp-ads-v2`（18 tools），**且全部是分页查询与趋势分析，零写操作**。【A，MCP 详情页 + 更新日志】

7. **对我们平台的意义**：这套架构**结构值得抄、能力不值得抄**。它的 Tools 层（18 个广告 tool）我们已经有更强的（积加 OpenAPI 25 个 `/operation/ads/*`）；它的 Skill 层（SKILL.md + 绑定 tool 白名单 + 可用用户）**正是我们模块3 缺的那块"规则版本化 + 权限"**；它的长期任务层（提示词 ≤2000 字 + 定时 cron + 失败重试 2 次）**可以低成本复刻**。

## 二、四层架构：一张图看清谁在干什么

```
┌─────────────────────────────────────────────────────────┐
│  第4层  长期任务 (long-task)                              │
│         定时器 + 固定提示词(≤2000字) + 绑定数字员工         │
│         失败重试2次/间隔5分钟 · 结果推送仅ERP站内消息        │
└───────────────────────┬─────────────────────────────────┘
                        │ 触发
┌───────────────────────▼─────────────────────────────────┐
│  第3层  数字员工 Agent (digital-employee)                 │
│         名称 + 状态 + 绑定 Skill[] + 备注(≤200字)          │
│         巡查维度(仅ASIN) / 巡查频次 / 筛选条件 / 单日上限   │
└───────────────────────┬─────────────────────────────────┘
                        │ 组合
┌───────────────────────▼─────────────────────────────────┐
│  第2层  技能 Skill (skill)                                │
│         SKILL.md: --- name/description/tools --- + SOP正文 │
│         + 可用用户[] + 分类 + public/custom 开关           │
└───────────────────────┬─────────────────────────────────┘
                        │ 调用
┌───────────────────────▼─────────────────────────────────┐
│  第1层  MCP Tools (19 个 server, 单 tool 1 点/次)          │
│         gerp-ads(21) gerp-ads-v2(18) gerp-order(3) ...    │
│         + sellersprite / sif-v2 / sorftime / xiyou        │
└─────────────────────────────────────────────────────────┘
```

**关键洞察**：积加把"能力"和"判断"彻底分开了。Tools 只负责取数（**全是 query，没有 execute**），Skill 只负责"怎么想"（提示词），Agent 只负责"用哪些技能"，长期任务只负责"什么时候跑"。**真正落地动作的那一环，它留给了人。** 这不是技术做不到，是产品定位（§6 阶段1）。

## 三、Skill 层：标准 SKILL.md + 工具白名单

### 3.1 数据结构（代码级证据）

前端 bundle `ch/index.8b651a97.js` 里，提交前把表单拼成 SKILL.md：

```js
// 变量名已还原
const buildFrontmatter = () => {
  const meta = { name: skillCode || "", description: skillDescription };
  if (tools && tools.length) meta.tools = tools;      // 工具清单进 frontmatter
  return `---\n${yamlStringify(meta, {indent:2, lineWidth:-1})}---\n`;
};
skillSummary = buildFrontmatter() + skillSummaryEditor.value;
```

即最终提交的 `skillSummary` 长这样：

```markdown
---
name: amazon-product-diagnosis
description: 对单个亚马逊商品做全方位经营诊断...
tools:
  - gerp_ads_v2_campaign_page
  - gerp_ads_v2_search_term_page
---
（这里是"技能概要"富文本正文，即 SOP）
```

**这说明三件事**：
- `skillCode` 不是给人看的编号，**它就是 SKILL.md 的 `name`**（官方要求"仅能使用小写英文、- 等符号"，正是因为要符合 skill 命名规范）。
- `tools` 数组写进 frontmatter，**服务端可据此做工具白名单校验**——技能声明的 tool 与用户可用 tool 求交集，这是它权限模型的落点。
- 正文是**富文本编辑器产出的 markdown**，官方建议包含六块：触发场景或话术、输入校验、输出格式、强规则约束、基本分析 SOP、需要调用的 Tools 说明。

### 3.2 表单字段（官方原文）

| 字段 | 约束 | 作用（官方原话） |
| - | - | - |
| 技能名称 | 0/20 | 自定义唯一标识 |
| 技能 code | 0/20，仅小写英文与 `-` | "辅助用于 AI 判断该技能作用，建议使用名称的对应英文" |
| 技能描述 | — | "辅助用于 AI 判断该技能作用，建议包含技能适用的场景、输出的内容概要等" |
| 技能分类 | 下拉枚举 | 选取对应分类 |
| 调用 Tools | 多选 | "一般数据分析类技能需要填写。（比如：创建一个文档内容解析的技能则不需要 Tools，但创建一个商品销量分析的技能则需要商品 Tools 和订单 Tools）" |
| 可用用户 | 多选 | 超管、创建者默认可用 |
| 技能概要 | 富文本 + AI 助写 | "技能的 SOP" |

### 3.3 官方技能清单（7 个，全部"产品运营"类）

| # | 技能名 | 官方描述（截断处保留原样） |
| - | - | - |
| 1 | Amazon评论分析（名后被打码） | 基于 Voice of Customer 方法对亚马逊商品评论做深度洞察，输出评分与情绪分布、好评差评根因、竞品口碑对比与改进建议 |
| 2 | Amazon评论分析 | 同上（两个同名技能，推测一个是旧版） |
| 3 | 意图分析 | 对用户评论进行精准的标签分类和意图识别，帮助团队快速定位问题并分发给相应部门处理 |
| 4 | Amazon商品诊断 | 对单个亚马逊商品（ASIN / 父ASIN / MSKU / SKU）做全方位经营诊断，覆盖销售、退款、利润、广告、流量、成本、促销、评论等维度，识别异常并给出优化建议与未来预测 |
| 5 | Amazon经营月报 | 以咨询顾问视角输出跨境电商经营诊断报告，先结论后证据，覆盖问题发现、原因解释与行动方案，面向老板与业务负责人 |
| 6 | Amazon销量预测 | 基于历史销量、活动、竞品信号，自动输出未来销量预测结果、置信度和解释说明（**注：输出内容不负责提供补货建议**） |
| 7 | 效果分析优化 | 评估单个亚马逊商品在一段优化工作有效期内的实际效果，对比立项期与基线期核心指标，做优化动作与指标变化的因果归因，并给出是否继续跟进优化的决策建议 |

**注意第 7 个**：它做的是"优化动作 → 指标变化"的**因果归因**，而不是"该不该降价"。这正是我们 06/07 文档里缺的一块——**执行后的效果校验**。积加把它做成了一个独立技能。

### 3.4 技能详情页 5 个 Tab

概述 / 所需 Tools / 数字员工（绑定了该技能的数字员工）/ 可用用户（可增删）/ 调整记录。

`public`（官方推荐）技能**无法停用**，只能从"可用技能"里移除；`custom` 技能有开关。

### 3.5 分类（服务端下发，非前端硬编码）

页面按钮：全部 / 通用技能 / 产品运营 / 统计分析 / **广告促销** / 财务 / 配送与发货 / 仓库与库存 / 采购。

前端 locale 里 `grep 广告促销` = 0，但分类来自 `GET /api/v1/skill/category/list` → **"广告促销"是服务端有、前端词表没有的新增分类**，说明积加正在往广告方向铺技能，只是还没有公开技能落地。

## 四、Agent 层：数字员工

### 4.1 字段极简

创建弹窗只有四项：**数字员工名称 / 员工状态（开关）/ 绑定 Skill（多选）/ 备注（0/200）**。

`状态=未开通` 时**不可发起对话、不可创建长期任务**。

### 4.2 列表页隐藏字段（比文档多）

文档只写了四列，实际截图有九列：

`数字员工 / 状态 / 工作处理时间 / 是否需要效果校验 / 效果检验Agent / 任务处理时间 / 拥有技能 / 备注 / 操作`

- **`是否需要效果校验`** 与 **`效果检验Agent`** 是文档里完全没有的两列 —— 说明积加在 Agent 层预留了"执行后由另一个 Agent 校验效果"的钩子（首行值 `--`，尚未启用）。
- 首行实测值：`30天 / 否 / -- / 7天 / 统计分析,Amazon商品诊断`。

**这条对我们很重要**：我们 07 文档的规则 25「执行异常监控」和规则 07「效果校验」，积加是用**独立的校验 Agent** 来做的，而不是把校验写进执行规则里。这是更干净的分层。

### 4.3 巡查配置（Agent 的"筛选器"）

数字员工不是"对全店跑"，而是先按条件筛商品：

| 组 | 字段 | 逻辑 |
| - | - | - |
| 范围 | 巡查维度（**当前仅 ASIN**）、巡查频次 | — |
| 必须同时满足 | 商品状态、近 15 天销量、时间范围 | AND |
| 满足其一即可 | 订单量环比降低(%)、流量环比降低(%)、流量环比-订单环比(%)、周期退款率(%)、差评数、**ACOS(%)** | OR |
| 上限 | 单日分析商品上限 | "并非越多越好，因同时会收到真实员工的处理速率和数字员工分析消耗 token 的影响" |

**ACOS 是筛选条件之一** —— 这是积加在 Agent 层唯一和广告直接挂钩的地方：它不调 ACOS，它**用 ACOS 挑出要分析的 ASIN**。

### 4.4 官方 3 个数字员工

| 名称 | 工作处理时间 | 任务处理时间 | 技能 |
| - | - | - | - |
| 通用商品优化数字员工 | 30天 | 7天 | 统计分析、Amazon商品诊断 |
| 优化效果分析数字员工 | 30天 | 7天 | 统计分析、Amazon商品诊断 |
| 商品优化数字员工 | 30天 | 7天 | 统计分析、Amazon商品诊断 |

三者技能完全相同，差异只在**提示词与筛选条件**——再次印证：**Agent 的差异 = 提示词差异，不是代码差异**。

## 五、长期任务层：定时器 + 固定提示词

### 5.1 三阶段路线（官方原文，最关键的一段）

| 阶段 | 名称 | 说明 |
| - | - | - |
| 阶段 1 | 半智能 | AI 出建议 → **真人判断** → **真人执行** ← **当前就是这个** |
| 阶段 2 | 半介入 | AI 按真人反馈执行 |
| 阶段 3 | 全智能 | AI 自判自执行 |

**这是判断积加 AI 定位最硬的一条证据**：它自己承认现在不执行。

### 5.2 后台执行链（官方原文）

```
定时调度器触发
  → 校验数字员工状态（是否下架 / 权限）
  → 加载任务固定提示词
  → 调用数字员工绑定的 Skill 执行 AI 推理
  → 生成完整分析报告
  → 存储执行记录与报告文件
  → 按推送配置分发
  → 标记成功/失败并记日志
```

**这条链里没有"执行动作"这一步**。整条链的产物是"报告"。

### 5.3 配置四 Tab

| Tab | 字段 | 关键约束 |
| - | - | - |
| 基础信息 | 任务标题 / 绑定数字员工 / 备注 | — |
| 任务指令 | 提示词 | **≤2000 字符**，官方："该提示词将作为每次定时执行 AI 对话的固定输入内容"；另有 `调用自动生成任务Skill` 开关（勾选后在工作台创建可跟进的任务） |
| 定时执行 | 执行周期（分钟/小时/日/周/月）、生效起止日期、失败重试 | 结束日期"不填表示长期有效"；**失败最多重试 2 次、间隔 5 分钟** |
| 结果推送 | 推送渠道 / 接收人 / 处理人（"选择平台账号"）/ 推送标题模板 / 附带报告文件 | **渠道目前仅 ERP 站内消息**，飞书/企微/邮件"后边酌情规划" |

周期文案模板（前端字符串，可直接复用）：
```
每 {interval} 分钟
每 {interval} 小时执行一次
每日固定 {time} 执行
每周【{days}】的 {time} 执行
每月【{days}】的 {time} 执行
```

### 5.4 真实运行数据（官方截图，泄露的运营实况）

某租户的长期任务列表 **共 77 条**，可见任务名与绑定数字员工：

- `广告诊断`（**多条**，周期分别为「每 1 小时执行一次」与「每日固定 21:38 / 21:57 / 22:00 / 20:17」）
- `经营诊断数字员工`、`亚马逊经营诊断与退货分析专家`
- `评论 / 商品诊断 / FBA费差异`、`自发货发货逾期预警`、`运营数字员工Test`、`测试`

任务 ID 形如 `TASK-79`。套餐卡：`AI旗舰套餐 312天后到期`、`剩余可用资源点 12,176.11`、`可自定义技能数 不限`、`可创建数字员工数 50个`、`赠送一年MCP基础版套餐`。

**读法**：真实客户把"广告诊断"配成**每小时跑一次**——这不是"自动化调价"，这是"高频巡检出报告"。同一天里 20:17、21:38、21:57、22:00 四个几乎连着的时间点，说明**客户在手动试探/调试周期**，而不是产品给了推荐值。

### 5.5 工作台 + 处理人看板

AI 出的建议落在**工作看板**，真人的跟进状态在**处理人看板**监控。这是"人机分工"的 UI 落点：AI 产出 → 看板 → 人认领 → 人执行。

**结构规律**：6 个实体 × 2（page + trend）+ negativeTarget + 2 个 creative + deal = 18。**`_page` 取明细、`_trend` 取趋势**——这是它省 token 的设计（官方明说"尽量少使用明细数据，用统计类 tools，明细可能成千上万条，统计只会有十几条"）。

**入参统一**：`count:boolean` / `current:integer` / `map:object`（扩展参数）/ `model:object` / `order:string`（默认 descend）/ `size:integer` / `sort:string`（默认 id）/ `specifyResponseFields:Array<string>`（**指定返回字段**）。

**`specifyResponseFields` 是关键设计**：AI 可以只要 3 个字段，避免一次返回 30 列。这是"省 token"最有效的一招，值得直接抄。

### 6.3 计费与限流

- **单 tool 调用成功 = 1 点**（明细里每次 `-1`）。
- 点数池**跨 provider 共享**：积加 MCP + 卖家精灵 + SIF + sorftime + 西柚洞察 共用一个池（官方卖点"买一个套餐享多方数据"）。
- 限流：基础版**单 tool 60/min**；进阶版以上**不限频**但受租户整体维度限流。
- 实测某租户：`本周期剩余调用点数 376,679 点 / 结束日 2027-04-27`，累计 **3,126 条**调用记录（157 页）。
- 流量包：1 个 = 1,000 次，有效期跟随套餐。

### 6.4 数据权限

`gerp_ads_v2_campaign_page` 详情页有 `数据权限说明 ✔ 支持按照ERP数据权限进行控制`。官方补充："当前仅支持**部分 MCP 的部分 Tools** 进行数据权限控制"。

即：**它把"这个 AI 账号能看哪些店铺的数据"下沉到了 ERP 的用户数据权限体系**，而不是自己在 AI 侧重建一套。这是它多租户设计的核心。

## 七、权限模型（三层：功能 / 操作 / 数据）

`用户管理 → 编辑用户 → 权限设置` 弹窗：

| 层 | 字段 | 值 |
| - | - | - |
| 数据 | `ERP权限授权` 开关、`已绑定ERP租户`、`ERP已验证手机号` | 绑了就用该 ERP 账号的数据权限 |
| 功能访问 | 会话 / 技能中心 / 长期任务 / 数字员工 / MCP市场 / 技能创作中心 | 勾选，**只能看不能操作** |
| 功能操作 | 新建对话 / 创建·编辑技能 / 创建·修改长期任务 / 创建·修改数字员工 / **调用MCP接口** | 勾选 |
| 配额 | `对话可用资源上限`（不设限 或 填数）、`可用技能`（多选）、`可用数字员工`（多选）、`可用Tools`（"不填则默认全部Tools"）、`MCP可用调用上限` | 逐人配 |

**"可用 Tools" 是它权限模型最细的一层**：官方示例"运营员工只开放运营相关 tools，财务仅开放财务相关 tools"。配合 Skill 的 `tools` frontmatter 声明，形成**双层白名单**（技能要什么 ∩ 用户有什么）。

## 八、对我们平台的启示

### 8.1 值得抄（三条）

| # | 抄什么 | 为什么 | 落到我们哪 |
| - | - | - | - |
| 1 | **Skill = SKILL.md（frontmatter + SOP 正文）+ tools 白名单 + 可用用户** | 规则不再是一段代码，而是一份可版本化、可 diff、可分配的文本。这直接解决我们 07 文档规则 26「策略版本化」 | 模块3 的 `rule_engine.py` 输出层：把每条规则落成一个 md 文件，而不是硬编码 if-else |
| 2 | **`specifyResponseFields` 式字段裁剪** | 一次只返回分析需要的字段，是省 token 最有效的一招（比"少查数据"更直接） | 我们 ingest 的 `raw_json` 已全存；给 LLM 看的那层应该只投影必要字段 |
| 3 | **`_page` + `_trend` 双接口设计** | 明细给证据、趋势给判断。LLM 先看 trend 决定要不要拉 page | 我们四张 fact 表可以直接派生 `_trend` 视图（按日聚合），不必让 LLM 扫明细 |

### 8.2 不能抄（四条）

| # | 为什么不抄 |
| - | - |
| 1 | **Agent 差异只靠提示词** —— 3 个官方数字员工技能完全相同、只差提示词。这种做法**不可回归测试**：改一个字，行为就变，没有 golden case。我们必须用确定性代码 + 参数化，提示词只做解释层 |
| 2 | **巡查维度只有 ASIN** —— 广告的最小决策单元是 **keyword / search term**，不是 ASIN。按 ASIN 巡检必然漏掉"某个词烧钱但商品整体还行"的情况 |
| 3 | **阶段1 只出建议** —— 这是它的产品定位（避免背锅），不是技术限制。我们要做的是"建议 + 一键执行 + 回滚快照"，把人的动作从"执行"降到"批准" |
| 4 | **结果推送只有站内消息** —— 对个人级工作台来说，站内消息等于没有通知。我们至少要 Webhook / 邮件 |

### 8.3 新增三条实现约束（回填模块3）

| # | 约束 | 依据 |
| - | - | - |
| 1 | **规则必须先声明它能用的数据源**（等价 tools 白名单），执行时校验"这条规则要的字段，这条规则被允许看" | 积加双层白名单（技能 tools ∩ 用户 tools）；我们 07 规则 24「零值语义保护」也需要"该字段是否被采集"的前置判断 |
| 2 | **每条规则必须绑定一个"效果校验"钩子** | 积加列表页有 `是否需要效果校验` + `效果检验Agent` 两列，虽然未启用，但方向正确；我们 07 规则 25「执行异常监控」缺这一环 |
| 3 | **提示词 ≤2000 字符，且必须可版本化** | 积加硬限制 2000；我们若走 LLM 复核（三道闸第一道），必须把 prompt 当配置管理，不能拼在代码里 |

### 8.4 一句话对比

> 积加AI 做的是"**让 AI 帮你写周报和诊断书**"；
> 我们要做的是"**让代码帮你改 bid，改完能回滚，改错能自愈**"。
> 前者卖的是"省人力"，后者卖的是"省广告费"。**同一个数据底座，两条完全不同的产品线。**
