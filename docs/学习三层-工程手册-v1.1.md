## 0. 一句话

现有引擎每天都在算，但它**只学了一样东西：今天这个对象偏离基准多少**。它学不到三件事——**这个偏离是不是噪声**、**这堆长尾词该怎么归类**、**我改了之后会怎样**。三层分别补这三件事。

（注意：第三件事不是「这两个词是不是一回事」。投放词之间**不判断相似性、不合并**——见 §5.1。语义层只对**搜索词**做归类。）

## 1. 先看数据说了什么

### 1.1 五个层级的齐性检验（scope=JL-高位下拉）

> **⚠ 2026-11-18 勘误：本节 z 值改为 p 值口径**
> **原来错在哪**：原表把 `z` 当检验统计量写进表格，但引擎从来不输出 z——`homogeneity()`（`engine/facts.py:964`）返回的是 `groups / clicks / orders / cvr / chi2 / df / p_value / significant`，判定字段就是 `p_value`（`engine/facts.py:993`）和 `significant = p < 0.05`。原表的 z 是用 `(chi2 − df) / √(2·df)` 事后反推的**近似值**，不是引擎算的，也不可复现：旧表词层 `chi2=7.20 df=5` 按该式得 0.70，表里写的是 0.82；同层重跑得 `chi2=7.25 df=5 p=0.203`，按该式得 0.71。**三个数互相对不上，说明原 z 值来源不明、且不可复现。**
> **怎么改**：判定一律看 p，`p < 0.05` 才算这一层有可辨差异。z 保留在旧表里作附注，但标明「z 是近似换算，p 是引擎实际算出的值，以 p 为准」。
> **p 值来源**：2026-11-18 实测，窗口 2026-11-02~11-15，scope=JL-高位下拉，直接取 `homogeneity()` 输出的 `p_value`。
> **两套数字不可混用**：旧表是窗口 2026-10-31~11-13 的结果，保留原样不改；下表是现行窗口 2026-11-02~11-15。两组组数、点击数、单数都不同，任何跨窗口相减/对比都是错的。

### 1.2 这条事实对现有引擎的判决

现在报告写「今天建议动 0 条」，读起来像坏了。**它其实是对的**——词层确实没有可判的动作。真正的问题有两个：

1. **报告没有把「本层无证据」说成人话**，而是输出空白，让人以为系统失灵。
2. **报告没有把组合层那条唯一显著的结论顶到头条**：本组合 CVR 0.63%，账户 1.81%，`chi2` 显著。但这条结论只能当**已知事实**写进头条（「本组合转化率是账户 1/3，广告层只能止损」），**不能变成「停投/挪预算」的可执行提案**——跨组合挪预算超出 P0–P1 的 scope（`policy_id=5`），且臂力器/美腰周转天数过长、跑步机/划船器已搁置，财务上不宜加投。

所以第一层的第一产出不是「救出更多建议」，而是**让报告能分层说话**。

## 3. 通用底座

### 3.1 段（segment）与层级

一切学习都挂在「段」上。段的键是字符串，层级用前缀区分：

```
account
portfolio:<portfolio_name>
campaign:<campaign_id>
match:<match_type>                     # 0=EXACT 1=PHRASE 2=BROAD
placement:<placement>                  # Top of Search / Detail Page / Other / Off Amazon
cluster:<cluster_id>                   # 第 2 层产出
kw:<keyword_text>
```

**继承顺序**（partial pooling 的链）：`kw → cluster → match/placement → campaign → portfolio → account`。
每一层都可以从上一层借力，借多少由 `κ` 决定（见 §4.3）。

### 3.2 表：`param_model`

```sql
CREATE TABLE IF NOT EXISTS param_model (
  segment_key   TEXT NOT NULL,
  metric        TEXT NOT NULL,          -- 'cvr' | 'cpc_ratio' | 'ctr'
  alpha         REAL NOT NULL,          -- Beta 后验 α
  beta          REAL NOT NULL,          -- Beta 后验 β
  n_obs         INTEGER NOT NULL,       -- 该段累计点击（或曝光）
  k_obs         INTEGER NOT NULL,       -- 该段累计转化
  kappa         REAL NOT NULL,          -- 该段所用先验强度
  kappa_source  TEXT NOT NULL,          -- 'mle' | 'inherited' | 'default'
  parent_key    TEXT,                   -- 上一层段键（可空）
  mean          REAL NOT NULL,          -- alpha/(alpha+beta)，读的时候不用重算
  lo95          REAL,                   -- 后验 2.5 分位
  hi95          REAL,                   -- 后验 97.5 分位
  window_start  TEXT NOT NULL,
  window_end    TEXT NOT NULL,
  updated_at    TEXT NOT NULL,
  PRIMARY KEY (segment_key, metric)
);
CREATE INDEX IF NOT EXISTS ix_param_model_metric ON param_model(metric, mean);
```

`lo95`/`hi95` 用正态近似算即可（`mean ± 1.96*sqrt(αβ/((α+β)²(α+β+1)))`），不引 scipy。

### 3.3 表：`learn_run`

```sql
CREATE TABLE IF NOT EXISTS learn_run (
  learn_run_id  INTEGER PRIMARY KEY AUTOINCREMENT,
  started_at    TEXT NOT NULL,
  finished_at   TEXT,
  window_start  TEXT NOT NULL,
  window_end    TEXT NOT NULL,
  layer         TEXT NOT NULL,          -- 'shrink' | 'semantic' | 'explore'
  segments      INTEGER DEFAULT 0,
  kappa_json    TEXT,                   -- 各层估出的 κ，便于回看漂移
  status        TEXT NOT NULL DEFAULT 'running',  -- running|ok|failed
  error         TEXT,
  notes         TEXT
);
```

**为什么单独一张表**：没有它，`param_model` 一变就说不清「是哪次学习改的」，回滚无从谈起。

### 3.4 学习器入口 `engine/learn.py`

```
python3 engine/learn.py shrink   [--window-days 14] [--exclude-days 2]
python3 engine/learn.py semantic [--window-days 14]
python3 engine/learn.py explore  --settle     # 回填到期实验
python3 engine/learn.py all
```

执行顺序（`all`）：`shrink → semantic → explore --settle`。
**纪律**：学习器只写 `param_model` / `term_cluster` / `explore_*` / `elasticity`，**绝不写 `decision_log`**。建议只能由 `rules.py` 出。

### 3.5 版本与回滚

- 每次 `learn.py` 跑前，把当前 `param_model` 快照到 `param_model_bak`（`CREATE TABLE ... AS SELECT`，带 `learn_run_id`）。
- 回滚 = `DELETE FROM param_model; INSERT INTO param_model SELECT ... FROM param_model_bak WHERE learn_run_id = ?`。
- **学习器失败不能阻断引擎**：`run.py` 里学习器调用包 `try/except`，失败则引擎回落到「无后验」模式（即今天的裸值行为），并在报告里标注 `learn_status=failed`。

### 3.6 三条硬约束

1. **学习器不产生建议。** 它只改参数，不改结论。
2. **学习器不调 LLM**（第 2 层的「簇→产品关系」判定除外，那是显式的、可关的、只在簇级别调用）。
3. **每个学习结果必须可追溯到窗口与 κ**，否则不进 `param_model`。

## 4. 第一层：跨对象收缩

### 4.1 学什么

学**每个段的真实 CVR（及 CPC 比率、CTR）**，以及**这个估计有多不确定**。产出两样东西：

- `mean` / `lo95` / `hi95` —— 给报告用（说人话的置信区间）
- `kappa` —— 给判定线用（见 §4.7）

### 4.2 数学

Beta-Binomial 共轭：

```
先验     p ~ Beta(α₀, β₀)
观测     k ~ Binomial(n, p)
后验     p | k,n ~ Beta(α₀+k, β₀+n−k)
后验均值  (α₀+k) / (α₀+β₀+n)
```

先验用「均值锚 + 强度 κ」参数化，这是让 κ 有意义的关键：

```
α₀ = p₀ × κ
β₀ = (1 − p₀) × κ
```

`κ` 的物理含义：**等效伪样本量**。κ=400 意味着「这个对象要攒 400 击，它自己的数据才和先验一样重」。对象有 n 击时，自身权重 = `n / (n + κ)`。

### 4.3 κ 怎么估

用**边际似然最大化**（不引 scipy，网格搜）：

```
logML(κ) = Σ_segments [ logBeta(α₀+k, β₀+n−k) − logBeta(α₀, β₀) ]
```

`logBeta` 用 `math.lgamma` 直接写。网格 `5..3000` 步长 5，撞到上界就记 `kappa_source='mle_capped'`（说明该层比预期更同质，是信息不是错误）。

**实测值（本店 2026-11-16）**：
- 词层（全账户 23 词 / 1975 击）：`κ ≈ 400`
- 词层（scope 6 词 / 723 击）：`κ = 3000`（撞上界）
- 组合层（11 组合 / 4079 击）：`κ ≈ 120`

**生产实现必须把网格上限提到 50000**，否则会一直撞上界、永远估不出真 κ。撞上界时记 `kappa_source='mle_capped'` 并在报告里标出。

**一个必须说清的后果**：scope 内 κ=3000 而总点击只有 723，意味着 `κ >> n`——先验几乎完全主导，每个词的后验都被拉向账户均值 0.63%（实测后验 0.61%–0.66%，差别不到 0.05pp）。

**所以收缩层在现在这个样本量下的实际作用，不是「区分哪个词更好」，而是「诚实地给出每个估计的不确定区间」。** 指望它把好坏词分开，是误解。等某天某个词攒到 2000+ 击，κ 的影响才会退到次要位置。

### 4.4 分层顺序

```
1. account        → 直接算，无先验（p₀ = 观测值，κ = ∞）
2. portfolio:*    → 先验取 account，κ 用组合层 MLE
3. campaign:*     → 先验取所属 portfolio 的后验均值，κ 用活动层 MLE
4. match:* / placement:*  → 先验取 campaign 后验均值，κ 用该层 MLE
5. cluster:*      → 先验取 portfolio 后验均值（第 2 层产出后才有）
6. kw:*           → 先验取所属 cluster 后验均值（无簇则取 portfolio），κ 用词层 MLE
```

**为什么先验逐层下沉而不是全用 account**：scope 收窄后 account 基线是 0.63%，但账户全量是 1.81%。如果词层直接向 1.81% 收缩，会把「本组合整体差」这个真实信号抹平。逐层下沉保证：**先承认「本组合就是差」，再在组合内部判断谁更差**。

**判定对象保持 `(keyword_text, campaign_id)` 不变。** Q13 结构冲突仍然照常报告「同词在几个活动」，那是告知，不是合并。

### 4.7 判定线自适应

现在的判定线是**账户级单一值**（`min_clicks(0.63%) = 254`）。改成**段级**：

```
need(segment) = ceil( ln(1−confidence) / ln(1−p_lo95(segment)) )
```

用 `lo95`（悲观端）而不是 `mean`，理由是判定线的作用是「防误判」，宁严勿松。

**实测效果（scope 内，κ=3000，正态近似算 lo95）**：

| 段 | n | k | 后验 mean | lo95 | hi95 | `need(lo95)` | 过线 |
|---|---|---|---|---|---|---|---|
| account | 1108 | 7 | 0.6318% | 0.4284% | 0.8351% | **375** | ✓ |
| kw `lat pulldown` | 281 | 2 | 0.6386% | 0.4099% | 0.8674% | **392** | ✗ |
| kw `lat pulldown machines` | 210 | 1 | 0.6216% | 0.3934% | 0.8498% | **409** | ✗ |
| kw `cable machine` | 111 | 0 | 0.6092% | 0.3797% | 0.8387% | **424** | ✗ |
| 搜索词层簇 `lat pulldown` 5 词（仅供理解，不作判定对象） | 574 | 3 | 0.6142% | 0.3993% | 0.8292% | 403 | — |

（先验 `p0 = 7/1108 = 0.6318%`，`κ = 3000`，`lo95 = mean − 1.645×SE`，`SE = sqrt(mean(1−mean)/(n+κ))`）

**两个必须承认的结论**：

1. **判定线变高了，不是变低。** 用 `lo95` 而不是 `mean` 做底，`need` 从账户级的 254 涨到 392（`lat pulldown` 词层）。所以收缩**不会让建议变多，只会让建议更少但更可信**。
2. **没有任何一段在「不合并投放词」的前提下过线。** `lat pulldown` 281 < 392，`lat pulldown machines` 210 < 409，`cable machine` 111 < 424。搜索词层簇 574 击能过 403，但那是**搜索词**的簇，不能拿来当**投放词**的判定对象（见 §5.1 否决二）。

   **所以第一层上线后，建议数不会变多，只会更严。** 这是预期的，不是失败。它买到的是「报告能诚实说本层无证据」。

**为什么 `lo95` 更低反而 `need` 更高**：`need` 的分母是「要能分辨的基线率」，基线越低，同样置信度需要的点击越多（小概率事件的方差更大）。收缩把区间收窄了，但收窄后的下界仍低于裸值，所以 `need` 更高。这是正确的保守方向。

## 5. 第二层：语义层

### 5.1 学什么

学**哪些搜索词是同一个东西**。产出一张 `term_cluster` 表，用来降低「这一堆长尾词要不要否」的人工判断成本。

**先说清楚它不做什么**（这一条是 2026-11-17 用户否决后加的，很关键）：

- **不合并投放词。** `lat pulldown` 和 `lat pulldown machines` 是两个独立需求，不并。
- **不为了过判定线而合并。** 靠合并凑样本量，与 `policy_id=4`（不足 3 条算正常，不为凑数而推）拧着。
- **不增加建议数量。** 它省的是人的判断时间，不是统计功效。

### 为什么不合并投放词——有铁证

```
投放词 lat pulldown          跑出的搜索词：lat pulldown(279击) / lat pulldowns(2击)
投放词 lat pulldown machines 跑出的搜索词：lat pulldown machines(186击) / lat pulldown machine(5击)
                                          / latpulldown machine(1击) / lat pull down machine(1击)
交集 = 空集    Jaccard = 0.00    重叠率 = 0%
```

两条流量**完全不交叉**。这说明它们是两批不同的人、两种不同的需求，不是同一个东西的两种叫法。

而且这两条在 2026-11-16 已经**分开批了「先观察」**（`decision_id=80/81`，`reject_reason_code=observe_no_execute`）。合并会让这两条已批结论失效。

**实测：scope 内任意两个投放词的搜索词 Jaccard 都是 0.00**——因为它们各自精准吃自己的流量（`lat pulldown` 99.3% 的点击就是本词）。既然全都重叠为 0，**一个都不该合并**。

### 那这一层还剩什么用

**只对搜索词聚类，帮人做否词的相关性判断。**

```
cable 系 72 个词分散在十几个簇里，合计 106 击 0 单 $75.04
  → 聚簇后，人只需对十几个簇判一次「跟我们产品相关吗」
  → 而不是对 72 个词逐个判
```

**但统计上仍然判不了**：P(106 击 0 单 | 基线 0.63%) ≈ 51%，不显著。所以这一层不产出「该否哪个词」的结论，只产出「这堆词是一类东西」的分组。

### 5.2 为什么不用 embedding

实测环境：
```
numpy 2.5.4          ✓
sentence_transformers ✗   torch ✗   transformers ✗   sklearn ✗   scipy ✗
magpie POST /v1/embeddings → 404（"书生端砚 may not serve this API"）
```
→ **没有 embedding 能力**。要么装 2GB 依赖，要么用确定性算法。选后者：可审计、零依赖、结果可解释。

### 5.3 归一化（确定性，先做）

```python
# ⚠ machine / machines 绝对不能进 STOP 表
#   上一版把它们当停用词删了，导致 tok('lat pulldown') == tok('lat pulldown machines')
#   == {lat, pulldown}，Jaccard=1.00，把两个独立需求并成一个。这是误并的根因。
STOP = {"for","with","and","the","a","to","of","in","at","on","home","gym","equipment","set"}
ALIAS = [("latpulldown","lat pulldown"), ("pull down","pulldown"),
         ("pull-down","pulldown")]
CORE  = {"pulldown","lats","lat","cable","smith","pulley","crossover","row",
         "fly","kickback","tricep","bicep","curl","attachment","stack","weight"}

def norm(term: str) -> tuple[str, set[str]]:
    s = term.lower()
    s = re.sub(r"[^a-z0-9\s]", " ", s)
    for a, b in ALIAS: s = s.replace(a, b)
    toks = [t for t in s.split() if t and t not in STOP]
    return " ".join(toks), set(toks)
```

### 5.4 聚类（种子式，禁止链式合并）

#### 先说一个必须避开的坑

我最初写的是「并查集 + Jaccard 双闸门」。跑出来是这样：

```
lat pulldown machines  67 词  685 击  4 单  $610.44
   ← 把 lat pulldown 和 cable machine 全并成了一坨
```

**为什么**：`lat pull down and low row cable machine` 这一个词同时含 `pulldown` 和 `cable`，它成了桥。并查集是**单链接**——只要 A 连 B、B 连 C，A 和 C 就同簇。一个桥词就能把两个无关品类焊在一起。

这不是参数没调好，是**算法选错了**。单链接聚类在有长尾同义词的场景里必然链式合并。

#### 正确做法：种子式（seed-based），不做词对词合并

```python
def cluster(terms: list[Item], jac_threshold=0.60) -> list[Cluster]:
    seeds: list[Cluster] = []
    for it in sorted(terms, key=lambda x: -x.clicks):   # 按点击降序，大词先成种子
        for sd in seeds:
            j = len(it.tok & sd.tok) / len(it.tok | sd.tok)
            shared_core = bool((it.tok & CORE) & (sd.tok & CORE))
            if j >= jac_threshold and shared_core:
                sd.members.append(it)
                break
        else:
            seeds.append(Cluster(seed=it, members=[it]))
    return seeds
```

**三条关键差别**：

1. **只跟种子比，不跟成员比**。新词必须与「簇的代表词」足够像才进来，不能通过链式传递搭便车。桥词 `lat pull down and low row cable machine` 与 `lat pulldown` 的 Jaccard = 1/4 = 0.25 < 0.60，进不来。
2. **阈值提到 0.60**（不是 0.34）。0.34 那档是我为了「多合并一点」加的，结果它把不同产品形态焊在一起。
3. **必须共享核心词**。`cable` 和 `pulldown` 都是核心词，但**共享**的核心词才算——`{cable}` 与 `{pulldown}` 交集为空，不合并。

#### 第三道闸门：投放词禁止合并（硬编码）

即使前面两道闸门都放行，**投放词（`fact_keyword_daily.keyword_text`）一律不合并**。这不是参数，是代码里的硬判断：

```python
def build_clusters(conn, window):
    # 只对搜索词聚类
    terms = load_search_terms(conn, window)      # fact_search_term_daily.search_term
    clusters = _seed_cluster(terms, jac_threshold=0.60)

    # 投放词单独成簇，永远不与任何词合并
    for kw in load_keywords(conn, window):       # fact_keyword_daily.keyword_text
        clusters.append(Cluster(seed=kw, members=[kw], kind="keyword", mergeable=False))
    return clusters
```

**为什么必须硬编码**：靠 Jaccard 判不出来。实测 `tok('lat pulldown')={lat,pulldown}` 与 `tok('lat pulldown machines')={lat,pulldown,machines}` 的 Jaccard = 2/3 = 0.67，仍然 ≥ 0.60 阈值。**只要靠 token 相似度判，这两个词就一定会被并。** 唯一的办法是代码层面禁止。

`cluster_verdict` 表加字段 `mergeable BOOLEAN DEFAULT 1`，投放词簇写 `mergeable=0`。任何下游代码要合并前必须检查这个字段。

## 6. 第三层：探索

### 6.1 学什么——先 CPC，后 CVR

**这是本层最关键的设计决定。** 7 单的窗口里，测「降 bid 会不会掉单」需要几百单的样本，做不到。但**测「降 bid 会不会掉曝光、CPC 会不会降」只需要点击**——1108 击足够。

所以：
- **第一期目标**：`Δbid → ΔCPC` 与 `Δbid → Δimpressions` 的弹性。这两个量每次点击都有观测，不需要等订单。
- **第二期目标**（需累计 ≥50 单/月后）：`Δbid → ΔCVR` 的弹性。

**不要跳过第一期直接测 CVR。** 那是拿 7 单去估三个参数，必然过拟合。

### 6.2 为什么必须随机

如果只在「觉得该降」的时候降，观测到的永远是「降了之后」的结果，没有「不降会怎样」的对照。**对照组必须由随机数产生，不能由规则挑。**

这就是 bandit 的核心：**故意让一部分对象跑在次优出价上，换取因果信息。**

### 6.3 选样规则（四个条件全满足才入选）

```
1. cost 在该组合内排前 20%（钱花得多，弹性才值得测）
2. 该对象 CVR 在后验 25–75 分位之间（太确定的不测，测了也学不到）
3. 无 policy 保护（freeze/position_hold/defend 一律排除）
4. 近 14 天无其他实验在跑（避免叠加效应）
```

每周最多 3 个对象。不足 3 个就少测，**不凑数**。

### 6.4 幅度与功效（实测，不是估）

先说结论：**CPC 弹性现在就能测，CVR 弹性现在测不了。** 这不是设计选择，是算出来的。

**CPC 的变异系数**（活动×日粒度，scope 内 90 个观测）：均值 $0.9594，标准差 $0.3642，**CV = 0.38**。

用两样本均值检验（双侧 α=0.05，power=0.8，`z = 1.96+0.84 = 2.80`）：

```
n_per_group = 2 × z² × CV² / δ²
```

| 要检测的 Δbid 效果 | δ | 每组所需点击 | 按 225 击/14天 需几天 |
|---|---|---|---|
| 15% | 0.15 | **101** | **约 7 天** |
| 25% | 0.25 | 37 | 约 3 天 |
| 10% | 0.10 | 227 | 约 15 天 |

→ **±15% 扰动，7 天就能判**。这是可做的。

**CVR 呢？** 用 `detect_power_orders(orders_per_day, relative_effect)`：

| 要检测的 CVR 变化 | 每组所需订单 | 按 0.5 单/天 需几天 |
|---|---|---|
| 15% | **698** | **1396 天** |
| 50% | 63 | 126 天 |
| 100% | 16 | 32 天 |

→ **要检测 15% 的 CVR 变化，需要 1396 天。** 三年半。

**所以第一期只测 CPC 与曝光弹性，CVR 弹性明确不做。** 这不是保守，是算术。

**扰动幅度定为 ±15%**，理由：
- 小于 10% 需要 227 击/组，要等 15 天，且容易被竞价噪声吞掉
- 大于 30% 有实际业绩风险（一个活动降 30% 出价可能直接失去头部位次）
- 15% 是「7 天可判 + 业绩风险可控」的交点

**周期定为 7 天**（不是 14 天）：
- CPC 弹性 7 天够（101 击 < 225 击/14天 ÷ 2）
- 7 天短，即使判断错了损失也小
- 与归因窗口的 bid 项（3–7 天）一致

**对象量级要求**：该对象 14 天点击 ≥ 200（才够 101 击/组 × 2 组）。scope 内满足的有 3 个活动（232 / 225 / 210 击）。**所以每周最多测 3 个臂不是人为限制，是数据上限。**

### 6.7 接入点

**探索任务必须走审批，不自动执行。** 因为「故意让某对象跑次优出价」是花钱动作。

流程：
```
learn.py explore --plan   → 生成 explore_arm(status='planned')
                          → 写一条 decision_log(action_type='explore', 待批)
                          → 奏折出现「本周探索提案 3 条」
用户打钩               → apply_answers 把 status 改 'running'，写 config_change_log
（人工或后续执行层）执行  → 实际改 bid
settle_at 到期          → learn.py explore --settle 回填 elasticity
```

**注意**：执行层（写广告后台）现在还没通。所以第一期探索只能在**有人工执行**的前提下跑。没有执行，这一层只能「规划」不能「学」。

### 6.8 预算与止损

**学费怎么算**（按实测花费，不是拍脑袋）：

scope 内点击最多的 3 个活动，14 天花费 $175.22 + $163.87 + $141.31 = **$480.40**，折每臂每周约 **$80**。

一个 15% 的出价偏离，若原 bid 已接近最优，效率损失约该臂花费的 **3–5%**（不是 15%——15% 是出价变动幅度，不是利润损失幅度）。

```
3 臂 × $80/周 × 4% ≈ $10/周
```

→ **学费约 $10/周，一个月约 $43。** 这个价格换「知道降 bid 会掉多少 CPC」，便宜。

- **止损线**：任一臂若 7 天内该活动 CVR 跌到后验 `lo95`（约 0.37%）以下，立即 `aborted` 并恢复原 bid。
- **止损第二线**：任一臂若 7 天花费超过 $120（正常 $80 的 1.5 倍），也 `aborted`——说明扰动导致曝光结构变化，花费失控。
- **累计上限**：同时最多 3 个 `running` 臂；超过则排队。
- **总预算闸**：`policy` 里加一条 `explore_budget_weekly = 10`（美元），超了当周不再开新臂。

### 6.10 失败模式

| 现象 | 原因 | 处置 |
|---|---|---|
| 弹性系数符号反了（降 bid 反而 CPC 升） | 位次溢价在叠加，实际出价没降 | 结算前核对 `config_change_log` 确认 bid 真变了；未变则该臂作废 |
| 所有臂 `evidence='weak'` | 单臂样本太少 | 累计到 `n_arms≥5` 才给 medium；这是设计预期，不是失败 |
| 臂永远 `running` | 执行层没通 | 报告显式列出「已规划未执行」的臂，提醒人工 |

## 7. 三层如何协同

```
06:10 ingest
07:00 引擎（rules.py）
      ├─ 读 param_model 后验（不用裸值）
      ├─ 读 term_cluster 做词族合并
      └─ 读 elasticity（无数据则用固定假设）
07:02 learn.py all
      ├─ shrink   → param_model（六层收缩 + κ）
      ├─ semantic → term_cluster + cluster_verdict
      └─ explore --settle → elasticity
07:05 诊断 agent（只处理「三层都判不了」的残余）
07:10 奏折
周一 08:00 归因 agent
周一 08:30 收敛 agent
```

**关键**：学习器在引擎**之后**跑，意味着**今天引擎用的是昨天的后验**。这是刻意的——避免同一天的数据既进模型又进决策（自我循环）。代价是延迟一天，可接受。

### 三层互补关系（用本店数字说话）

| 问题 | 单靠规则 | 加上第 1 层 | 加上第 2 层 |
|---|---|---|---|
| lat pulldown 该不该降 bid | 225 击与 56 击，各自 < 254 → 无法判 | 段级线升到 392/409 → 仍无法判 | **仍无法判**（且不该靠合并去凑，见 §5.1） |
| 72 个 cable 词怎么办 | 72 个独立对象，全「样本不足」 | 同上 | **聚成十几簇，每簇仍样本不足；但只需对簇判一次语义，不用逐词判（省判断成本，不增功效）** |
| 本组合整体如何 | R30 一条告警 | **组合层 p=0.000（4705 击 / 82 单，窗口 2026-11-02~11-15），进头条作「已知事实」** | 同左（不构成挪预算提案） |
| 降 bid 会掉多少单 | 无从得知 | 无从得知 | 无从得知（需第 3 层） |

## 10. 明确不做的事

1. **不做深度学习。** 7 单的样本量，任何神经网络都是过拟合噪声。`κ=3000` 这个数字就是证据：连贝叶斯都认为词层没有信息，神经网络只会把它记住。
2. **不做跨账户迁移。** 那是 B 阶段的事，现在样本量不够建立可迁移的先验。
3. **不做自动执行。** 探索臂的 bid 变更仍需人工执行，因为写权限未开，且这是花钱动作。
4. **不用 LLM 算统计量。** LLM 只判「簇→产品关系」这一件语义事，其余全走确定性算法。
5. **不追求「每天都有建议」。** 没有证据时报告就该说没有证据。这是特性不是缺陷。
6. **不为了让数字好看而放宽目标 ACOS。** 放宽到 70% 只是承认现状，不是改善。目标该由人定，不由系统迁就。
