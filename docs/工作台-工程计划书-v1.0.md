## 一、目标与非目标

### 目标

把今天只能看 md 的奏折，变成一个能打钩、能追问、能看趋势的本地 app。三件事：

1. **审批台**——每天 10 分钟内把 `decision_log` 里该批的批完。批完生成执行单，你照着改广告后台，回来标「已改」，归因窗从那一刻开始计时。
2. **驾驶舱**——六个面板把「钱花在哪、哪层有证据、谁在抢同一个词、外部发生了什么、上个月改的东西后来怎么样了」摊开。
3. **四个 agent 岗位**——诊断（出疑问清单 + 反对规则建议）、归因（回填 outcome）、收敛（验证假设）、对话（只读问答）。**agent 只做否决与质疑，不产生新建议。**

### 非目标（明确不做）

- **不做自动执行**。广告后台写权限没开，也不该开。工作台只写到 `decision_log` 的审批列，物理上碰不到 Amazon。
- **不做 agent 生成建议**。建议唯一来源是 `engine/rules.py`。agent 输出进 `agent_objection` / `agent_eval`，永远不会 INSERT `decision_log`。
- **不做跨账户迁移**（B 阶段）。
- **不做深度学习**。scope 内 7 单，任何神经网络都是过拟合。
- **不引入图表库**。15 天 6 个指标，echarts 要 30+ 依赖，手写 SVG 300 行搞定。
- **不重建调度器**。定时只有一条链（`adsdesk/chain.py` + launchd `com.baoyanan.ads-chain`），工作台不自己定时。
- **不改 `engine/facts.py:677` 聚合键、不改 `engine/rules.py:417`/`:592` 动作落点**（用户 2026-11-17 否决，见手册 §1.1b）。

## 二、前置结论：五条必须先说清的实测事实

写排期之前，这五条会直接改变你对「做完能拿到什么」的预期。不认这五条，后面的工期估算都会失真。

### 2.1 今天的奏折正文是 0 条，不是 7 条

`engine/run.py --dry-run` 实测（窗口 2026-11-01~11-14）：

```
[事实] $966.25 / 1191 击 / 7 单 / ACOS 75.73% / CVR 0.59%
[事实] 盈亏平衡 CVR 1.48% → 目标不可达；判定线 274 击（0 单）/ 509 击（1 单）；CPC 系数 1.790；地板 $0.40
[规则] 6 条建议，17 条被保护拦下
[奏折] 正文 0 条，溢出 0，不够线 0，问题 1，结构冲突 3
```

`decision_log` 落库 run #9 只有 1 行：`89 | R30 | alert | high | 全店`。

**所以审批台第一期上线时，打开会看到「今天没有达到判定线的动作」+ 1 条问题 + 3 组结构冲突。** 这不是 bug，是统计诚实的结果（详见 §2.2）。如果为了「有东西可批」而放宽门槛，工作台就变成了骗自己的玩具。

### 2.1.1 不放宽门槛，但给出显式出口（S1 已落地，2026-11-19）

判定线不动。但「等不起」是真实处境：旺季前预算有限，一个词已经花掉 $31 零成交，人看着趋势比看着 p 值更有把握。所以「只看不动」区给出显式二次确认入口：

| 引擎说 | 人能做的 | 账本里留下什么 |
|---|---|---|
| `gate_reason`（原话，如「证据不够：115 击 1 单，按基线应出 0.58 单；判更差需 597 击」） | 点「强制批准」，必须写理由（≥8 字） | `gate_reason` 保留引擎判断；`override_by` / `override_reason` / `overridden_at` 记人拍的板；理由进 `reason_hit`（`reason_code='owner_override'`，`answer_type='override'`） |
| — | 点「已改」（真去广告后台改了才点） | `executed_at` + `attribution_due_at`，归因窗从这一刻起算 |

三条边界：

1. **`gate_reason` 只由引擎写**，`DECISION_WRITABLE_COLUMNS` 不含这一列 —— 审批侧不能把「证据不够」洗成「证据够」。
2. **observing 落库但不进待批队列**（run #100 起 `status='observing'`；`v_open_decisions` 与 `GET /pending` 仍只要 `proposed`）。有 `decision_id` 只是为了让前端能引用它、能记 override。
3. **强制批准的条目在引擎重跑时不被剔除**（`_upsert_observing` 对 `approved` 返回 `reused`）。否则跨天之后它从页面消失，人再找不到它去标「已改」，归因窗永远不开。已 `executed` / `rejected` 的才移出。

实测（run #100~102，真库）：`decision_log` 出现第一条 `approved → executed`，`attribution_due_at=2026-11-26`；页面「只看不动」卡三条各带 gate_reason 与「强制批准」按钮，批准后变「已强制批准 + 已改 + 你当时的理由」，点「已改」后变「已改 · 归因至 2026-11-26」。

### 2.1.2 归因回填：到期真的会回看，而且不把全店的下滑算到一个词头上（2026-11-19）

打钩、标已改、等 7 天 —— 之前链到「等 7 天」就断了：`outcome_7d_json` / `outcome_14d_json` / `outcome_filled_at` 三列建好了、驾驶舱也在读 `where outcome_filled_at is null`，但**没有任何东西会去写**。到期那条会一直挂在「该回填了」，人得自己翻报表。

补上的是 `adsdesk/agents/attribute.py`（链上第 ④ 步，`chain.py` 排在 ingest → engine → diagnose 之后；旧 plist `com.baoyanan.ads-attribute` 已停用）。它做三件事：

| 步 | 做什么 | 落在哪 |
|---|---|---|
| ① 找 | `status='executed'` 且 `outcome_filled_at is null`，到期看 7 天；已看过 7 天的，第 14 天再补一次终局 | 账本自己的 `executed_at` / `attribution_due_at`，不另建「动作类型→天数」表 |
| ② 算 | 执行前 N 天 vs 执行后 N 天，按 `entity_type` 选事实表（keyword→`fact_keyword_daily.keyword_id`、search_term→`fact_search_term_daily.search_term`、campaign、placement）；同时算**同期全店**同一窗口 | `before` / `after` / `account{before, after}` 三段，每段给 clicks/orders/cost/sales/cvr/cpc/cpo/acos |
| ③ 判 | 先扣掉「全店同期也在变」那层，再看方向 | `verdict` ∈ improved / worsened / flat / insufficient / no_data + 一句 `basis` |

判定的三条硬规矩（都是踩出来的）：

1. **执行后零单时不看「每单成本」** —— 分母是 0。改比花费，并同样扣掉全店同期花费变化。
2. **零单是不是「改坏了」，取决于同期本来该出几单**。用全店同期 CVR 反推期望单数：`expect = after.clicks × acct_after.cvr`。不到 1 单就判 `insufficient` 并明说「零单在噪声内，判不出是谁的错」，不硬扣帽子。
3. **前后都出单才比每单成本**，且看的是 `相对变化 = 该对象变化率 − 全店变化率`，带宽 ±15%（`RELEVANCE_BAND`，工程默认不是统计结论，注释里写明了）。

实测（临时库把 #153 的窗口前移，构造出 7 天已到期的情形）：

```
insufficient：执行后零单：花 72.12（前 75.47，-4%）；全店同期花费 +39%，
相对少花 44%；1 单 → 0 单（全店每单成本同期 +54%）。
按全店同期 CVR，这 53 击本来也只该出 0.79 单，零单在噪声内，判不出是谁的错。
```

同一份数据若只看绝对数字，会得出「降 bid 后零单 = 改坏了」；扣掉全店那层才发现那周整个账户的每单成本都在 +54%，这个词的零单落在噪声里。**这就是必须有对照、必须宁判 insufficient 的原因。**

写库规则：7 天那次写 `outcome_7d_json`，同时把 `outcome_14d_json` 写成 `{"pending": true}` 占位（让页面知道「看过一次、还差终局」）；只有 14 天那次才写 `outcome_filled_at` —— 一旦写它，这条就从驾驶舱的跟踪列表里消失。判定结论另外记一条 `reason_hit`（`answer_type='attribution'`, `reason_code='outcome_7d' / 'outcome_14d'`），失败静默：旁证不该挡住回填。

驾驶舱侧（`Cockpit.tsx` ⑥ 归因窗追踪）：跟踪表的状态列按 `seen_7d` 分「该回填 7 天 / 该看 14 天终局 / 7 天已看等终局 / 观察中」；下方新增「已回填」表，给判定 tag + 那句话，并注明「比的是相对全店的变化，不是绝对数字；执行前后对比不是 A/B 测试」。

### 2.1.3 诊断 agent 挂了一整天，是因为它只有一条路（2026-11-19）

当天 07:18 那次诊断，页面一整天写着「跑失败了 · 网关响应超过硬截止 600s 仍未返回，已放弃（auto/deepseek-v4.1-flash-1017）」。根因两条，都在「只有一条路」：

1. `~/Library/LaunchAgents/com.baoyanan.ads-diagnose.plist` 里写死了 `--model`，而代码把这个值当成**唯一**模型。`gateway.FALLBACK_MODEL` 那个常量从头到尾没被任何代码引用过 —— 名义上有备用模型，实际没有。
2. `timeout=600` 且 `GatewayError` 不重试。那个模型在网关排队，一次排队就等于当天没有诊断。

改了三处：

| 项 | 改前 | 改后 | 依据 |
|---|---|---|---|
| 模型 | 单个（plist 指定的那个） | 链路 deepseek → glm-5.3 | 成功那几次 deepseek 123 秒、glm 331 秒；都试才有当天出结论的可能 |
| 单模型硬截止 | 600s | 300s | 成功只要 123 秒，2.4 倍余量；两个模型合计 600 秒上限 |
| max_tokens | 64000 | 48000 | 实测 completion 落在 18085~33966；真被截断也不致命了，链路会换模型 |
| `--model` 语义 | 唯一模型 | 链首（首选，其余照旧兜底） | plist 不动也不会砍掉兜底 |

四条边界，都是「不假装成功」的同一件事：

1. **降级不是失败，但必须留痕。** `chat_with_fallback` 把每个模型的失败原因拼进 `out["fell_back"]`，日志打一行「降级：前面那个没答上来 —— …」。只报最后一个，会把「主用排队、备用截断」显示成「备用截断」，下次照着修还会踩同一个坑。
2. **账本记真正答话的模型。** `agent_run.model` 写的是网关返回的 `r["model"]`（实测 `group/auto-deepseek-v4-1-flash-1017`），不是预期的链首。否则回头查「那天为什么结论变了」，会看到一个根本没参与过的模型名。
3. **截断不再等于当天失败。** 以前 `finish=length` 直接抛错收工；现在它是降级理由之一，换下一个模型接着试。
4. **跑飞的进程照样会被收。** `_reap_stale` 仍是 30 分钟，是单模型 300 秒的 6 倍、整条链路的 3 倍。

实测（2026-11-19）：dry-run 3 分 32 秒、tokens (12342, 33966)；真跑 3 分 10 秒、`agent_run` #36 记 `ok`、tokens (12342, 30909)，`memorial` run 102 的 `agent_state` 由 failed 变 ok，页面标题变成「诊断 agent group/auto-deepseek-v4-1-flash-1017 · 4 个疑问 · 3 条反对 · 7 条待验证」。两次都是首选模型直接成功，没触发降级 —— 所以降级这条路只有代码和日志，还没有真实战例。

### 2.1.4 归因结果真的反哺到提案了（2026-11-19）

2.1.2 让「到期会回看」成立，但回看的结果只躺在 `decision_log.outcome_*` 里，规则层从头到尾没读过它 —— 系统会记得上次改坏了，下次提案时却一点都不会因此谨慎一分。反馈环在最后一米是断的。

补上的是 `engine/record.py`，做三件事，方向都是「少说、别吹」：

| 做什么 | 怎么做 | 为什么不这么做会更糟 |
| --- | --- | --- |
| 给每条决策附战绩 | 同规则、同对象各自的 improved / worsened / flat 统计，写进 `context`，跟着 `pack.json` 到页面 | 人看不到「这条规则最近准不准」，只能凭感觉信或不信 |
| 按战绩收紧名额 | 一条规则样本够、且变差过半，今天能占的待批名额减一格（下限 1） | 反复改坏的规则会一直霸占注意力，把位置挤给更靠谱的规则 |
| 同对象反复改坏就本届不进待批 | 判差 2 次以上 → 挪进观察区，`gate_reason` 写明是哪几次、什么结论 | 同一个词连改三次都不灵，第四次还自动进待批，是在赌运气 |

三条口径，都是为了不被噪声牵着走：

1. **只认已出方向的判定**（improved / worsened / flat）。`insufficient` 和 `no_data` 不进分母 —— 把「证据不够」算成「没变好」，会让一条规则因为运气差被永久降级。
2. **14 天终局优先于 7 天。** 同一条决策先有 7 天、后有 14 天时只算一次，且用终局。
3. **样本少于 3 次时 `hit_rate` 返回 `None`，不返回 0 或 1。** 一次执行说明不了任何规则的好坏，返回一个数字就是在装懂。

接入点（全部在 `engine/`）：

- `facts.Facts` 加 `record` 字段；`run.py` 在 `build_facts` 之后填 `f.record = record.build(conn)`，日志打「[战绩] 近 90 天 X 次有结论的执行：好 A / 差 B / 平 C」。
- `run.py` 在 `rules.run_all` 之后 `record.annotate(res.decisions, f.record)`（日志带「N 条附了历史战绩」），在 `hold_recent_observe` 之后 `record.apply(pack, f.record)`。
- `report.compress` 用 `record.quota_cap(...)` 覆盖 `QUOTA.get(rule_id, DEFAULT_QUOTA)` 的结果。
- `report.pack_json` 的每条决策多两个字段 `rule_record` / `object_record`；没有就整条不出现（空字符串会让前端多画一行没内容的字）。

页面（`Approval.tsx`）：待批卡在理由下面多两行「· R01 过去 4 次有结论的执行：…」「· 这个对象过去 3 次…」；只看不动卡的说明格也带对象战绩（规则战绩用小一号字，避免同一个规则在两行重复时太吵）。

实测（临时库构造 8 条 executed 样本，真库现在 0 条历史）：

- `python3 engine/record.py --db …` → 「7 次有结论（好 2 / 差 4 / 平 1）」；R01 4 次（1 好 2 差 1 平）、R22 3 次（1 好 2 差）、R09 只有 1 次 insufficient 被判「样本还不够」。
- `quota_cap`：R01 3→2、R22 2→1、R09/R99 原样不动（样本不够 / 无历史）。
- `annotate`：R01 的决策挂上战绩，R99 什么都不挂。
- `apply`：`lat pulldown`（对象被判差 2 次）被挪进观察区，`gate_reason` 为「这个对象已被改动 3 次、其中 2 次判为变差（2026-11-10 判为变差；…）。本轮不自动进待批 —— 要动就显式强制批准。」
- 页面核对：R01 的两条观察项显示规则战绩、`lat pulldown` 那条多一行对象战绩、`cable machine home gym`（R21 无样本）两行都不出现。

### 2.1.5 断言兑现率：它准不准，现在有数字了（2026-11-19）

诊断 agent 每轮会写下若干条「可验证断言」（`agent_eval`），比如「日均 CPC ≥ $1.20」「T+3 clicks ≥ 1.2 × T+1 clicks」。这些断言到期后要有人判真假 —— 否则「一周后看兑现率决定要不要让它真的挡建议」永远只是一句注释。

**原来的状态（实测）**：`converge.py` 写完了 1323 行，但 `grep -rn converge` 全项目只命中 `context.py` 里的一句注释 —— 没有 launchd、没有 API 调用、没有前端。135 条断言全部 `pending`，兑现率从来没有被算过一次。

**这一轮做的四件事**：

| 事 | 落在哪 | 说明 |
|---|---|---|
| 接上定时 | `~/Library/LaunchAgents/com.baoyanan.ads-converge.plist` | 每天 **07:15**，排在 diagnose（07:05）之后 —— 当天新写的断言当天就能被扫一遍到期日 |
| 算兑现率 | `adsdesk/api/routes/memorial.py` `_agent_view` 增 `score` | 跨**全部** run 累计，不是只统计这一轮 |
| 显示兑现率 | `adsdesk/web/src/pages/Approval.tsx` 诊断卡标题 + 一行小字 | 标题：「兑现 5/7」；小字：「7 条断言已判：对 5 / 错 2（71% 兑现）；另有 127 条还在等判定日、1 条判不了。样本 7 条，先别当成定论。」 |
| 类型 | `adsdesk/web/src/lib/api.ts` 新增 `AgentScore` | `rate: number \| null` |

**三条口径（都在代码注释里写明了理由）**：

1. **分母只算 correct + wrong。** `unverifiable` 是「数据齐了、断言本身判不出」（比如断言要一份库里根本不存在的对照数据），这是**永久结论**，不是拖延；`pending` 才是「数据没追平 / 还没轮到」（临时状态，下一轮自动重判）—— 两者混算等于拿天气赖账。
2. **一条都没判出来时 `rate` 返回 `null`，不是 0.0 也不是 1.0。** 返回 0.0 会被读成「全错」，返回 1.0 会被读成「全对」，两个都是撒谎。前端对 `judged === 0` 单独显示「它过去的断言还没有一条到判定日：N 条在等。现在还不能说它准不准。」
3. **样本量写在脸上。** 有数字时也会跟上「样本 N 条，先别当成定论」—— 3 条里对 2 条不是「67% 准确率」。

**实测**：

- 真库跑 `python3 converge.py`（as_of 2026-11-19）→ 「到期断言=1 条」，#74 被判 `unverifiable`：理由是「该断言要对比 11-16 clicks 在 T+1（11-17）与 T+3（11-19）两次读数，但事实包只给出账户 11-01~11-18 的聚合数据（clicks 5779），既无按天的 clicks 明细，更无两次快照的历史读数；且数据覆盖止于 11-18，早于 T+3 读数日」—— 模型调用 1 次。
- 换算远期：`--as-of 2026-12-31 --no-llm` → 到期 39 条、correct 2 / wrong 1 / unverifiable 36，绝大多数是「窗口没走完」，这是数据追平问题不是代码问题。

#### 2.1.5.1 装 launchd 时揪出来的真 bug：临时状态被写成了永久结论（2026-11-19）

接 plist 只是接线，真正卡住兑现率的是判定日这一天的边界。**现象**：`agent_eval` 135 行全是 `pending`，最早判定日 11-19，但 11-19 这天跑出来的结果不是「判了」而是「判不了」。

**根因（三层，逐层实证）**：

1. **到期日当天，数据物理上不可能齐。** `ingest`（06:10）每天只拉到 D-1，`converge`（07:15）拿到的事实止于昨天；而断言窗口的终点普遍就写在到期日当天，于是 `_window_state()` 在到期日当天永远是 `partial`。
2. **旧代码把 `partial` 写成 `unverifiable`。** `_gate()` 与 `_ev_decision_log()` 都用 `unverifiable` 表达「窗口没走完」。
3. **`unverifiable` 一旦落库就再也判不了。** 幂等写是 `update agent_eval ... where verdict='pending'`，写完就不再是 `pending`，下一轮永远扫不到它 —— **临时状态被写成了永久结论**。

真库实证：`#74`（断言「T+3 clicks ≥ 1.2 × T+1 clicks」，T+3 读数日 = 11-19）在 11-19 12:28 那轮被判 `unverifiable`，理由是「数据覆盖止于 11-18，早于 T+3 读数日」。它本来只该等到 11-20 再判。

**修法**：把「没追平」从结论里拿掉，改成不写库。

| 闸门 | 位置 | 旧行为 | 新行为 |
|---|---|---|---|
| 覆盖闸门（比值类） | `_gate()` future / partial 分支 | `unverifiable` | `pending`（不写库） |
| 覆盖闸门（计数类） | `_ev_decision_log()` `state != 'covered'` | `unverifiable` | `pending`（不写库） |
| **进模型前** | `run_once()` 分派 | 无 —— 实体抽不出就直接问模型 | `_window_state(win, cov) != 'covered'` → `pending`，**不问模型** |
| 可见性 | `converge_run` 新增 `n_deferred` 列 | 只有「到期/回填」，看数像卡住 | 「到期 1、回填 0、**暂不判 1**」一眼看出在等数据 |

第三道闸门是实测逼出来的：`#56` 的 method 没写日期区间 → 窗口 = `起始~2026-11-20`，实体又抽不出 → 直接进模型 → 模型按裁剪过的事实包只能回 `unverifiable` → 又被钉死。修之前它在副本里就是这么被钉的。

### 2026-11-20 补：`unverifiable` 的复活通道 + 读数快照

三道闸门解决了「数据没追平」，但没解决另一件事：**`unverifiable` 一旦写进去就是永久结论**（幂等 `UPDATE` 只改 `verdict='pending'` 的行）。当我们后来新修了一条证据通路，那些「因为缺证据而 unverifiable」的断言就永久停在了一句已经不成立的话上。

实测 `#74`：2026-11-20 上午被判 `unverifiable`，actual 明写「没有任何按日或按次快照的 clicks 数值」。当天下午建了 `fact_read_snapshot` 并回填 11-01~11-19 基线（76 行），它立刻就能判了 —— 但没人把它放回 `pending`。

| 改动 | 位置 | 为什么 |
|---|---|---|
| `fact_read_snapshot` 表 | `adsdesk/api/schema.sql` ⑧ | `fact_*_daily` 是 upsert 覆盖，同一 `report_date` 重拉一次就把上次读数抹了。「T+3 ≥ 1.2 × T+1」这类断言要的是**同一天的两次读数**，库里只剩最后一次 |
| 只在读数变化时追加 | `ingest/ingest.py` `snapshot_readings()` | 日更链每半小时跑一次，全量追加会让表膨胀到百万行而 99% 什么都没变。代价：读数没变化时不会有新行，「重拉过但数没变」只能从 `run_log` 看出来 |
| `_ev_reread` 判定器 | `adsdesk/agents/converge.py` | 认两种写法：`T+3 clicks ≥ 1.2 × T+1 clicks`（跨日型）、`后一次 ≥ 前一次 × 1.3`（顺序型）。跨日型遇到「同一天多次读数」判 `pending`；顺序型不挡 —— 它没承诺跨天 |
| `revive_unverifiable()` | 同上，`--revive-only` | 只复活 actual 里明确写着「缺某样东西」且那样东西现在已有数据的。不做批量重置 —— 其它原因 unverifiable 的证据可能真的永远拿不到 |
| `这一天的读数轨迹` | `_fact_pack()` | `_ev_reread` 判不了的写法（「比本窗口内记录的值高至少 30%」不带倍数）交模型时，把读数序列摆给它 |

### 2026-11-20 再补：从备份库回收历史读数（`ingest/backfill_readings.py`）

建表只能解决「以后」，解决不了「以前」。`#74` 问的是 11-16 那天的两次读数，两次都发生在建表之前 —— 按「表建晚了所以判不了」处理是错的，因为**读数并没有丢**：`ingest/data/` 下留着一串 `.bak-*` 备份库，每个都冻结了它那一刻的读数，**备份文件的 mtime 就是 `observed_at`**。

回收出来的真实轨迹（`dataset=campaign`）：

|---|---|---|---|
| 2026-11-16 | `175`（11-17 备份）→ `399`（11-18）→ `400`（11-19） | 400/175 = **2.2857** | ≥ 1.2 → 成立 |
| 2026-11-15 | `212`（11-16 备份）→ `486`（11-18） | 486/212 = **2.2925** | ≥ 1.3 → 成立 |

→ **agent 当初的判断是对的：T+1 拉数低报约 2.3 倍，T+3 重拉才补回。** 这个结论此前只能靠「日志里说拉过」推测，现在是两个真实读数相除。

| 改动 | 位置 | 为什么 |
|---|---|---|
| `ingest/backfill_readings.py` | 新文件，约 300 行 | 扫 `.bak-*` 备份库，按 `report_date` 汇总后写成快照行。**不 import `ingest.ingest`** —— 那个模块 import 时会拉起 `jijia_client`，要凭证要网络，回填不该有那层依赖 |

### 2.1.6 让 agent 看见自己的旧账，也让它知道断言写坏了（2026-11-19）

兑现率只是给人看的数字，agent 自己看不到。于是同一个口径错误它能连犯两轮：
11-18 断言「ACOS ≥ 0.60」实测 0.42，11-19 又用同样的推算方式推落点。
这一节做两件事：把判定结果喂回它的输入；把「断言能不能验」也算成一个指标。

| 动作 | 落点 | 做法 |
| --- | --- | --- |
| 旧账进输入 | `adsdesk/agents/context.py` `_self_check()` | 每次诊断附 `self_check`：`judged / correct / wrong / rate / verifiable_rate`，加 `wrong_claims` 5 条、`correct_claims` 3 条（各带 `claim/expected/actual`） |
| 用错了怎么办 | `prompts/diagnose_v1.md` | 正文加 6 条说明：这是它自己的历史不是别人评价；`unverifiable` 不算它错；`rate` 分母只含已判对错，为 null 不代表不准；若旧账与今天的问题直接相关，先说那条旧账 |
| 断言写坏了也算指标 | `memorial.py` `_agent_view` | `score` 增加 `verifiable`（进过判定的条数）与 `verifiable_rate`（judged / verifiable），前端在分母 ≥ 5 且 < 60% 时提示「先改断言再谈准不准」 |
| 排障要全量 | `diagnose.py` `--out PATH` | dry-run 原来只打印前 800 字，核不了「它到底怎么答的」 |

**实测（临时库喂 2 错 1 对，跑 `diagnose.py --dry-run --out`）**：4 个疑问里的 D4 自己写了
「（上次我押 T+3 重拉点击会变多，实测只有 0.8 倍，这次不拿重拉当变量。）」—— 它读到的是
`wrong_claims[0]` 的 `claim` 与 `actual`，并且改的是**推理方式**，不是复述一遍认错。
这是这一节唯一值得记的证据：喂旧账确实改变产出，不只是让 prompt 变长。

**三条边界**：

- **只喂已判的**。`unverifiable` 不进 `wrong_claims` —— 那是「判不了」，喂进去会让它莫名变保守。
- **错的 5 条、对的 3 条，不对称**。只喂错会过度自我否定；全对称又会让「我大部分对」盖过具体教训。
- **不给它权力**。兑现率现在决定的是**话的读法**（「先别当定论」/「先改断言」），不是能不能挡建议。
  要真的让 `agent_objection` 进 gate，至少得等 `judged ≥ 3` 且攒出可信的 `wrong_rate` —— 现在 `judged = 0`，
  真库里连一条都没走到判定日，任何调权都是拿噪声当证据。

### 2.1.7 整条链从来没在真机上按时跑过：五个固定钟点换成「守夜人」（2026-11-19）

**触发点**：用户一句「我每天 9 点才开机」。查下来这不是习惯问题，是调度方式选错了。

**实测证据（当天）**

| 任务 | plist 排期 | launchd 实际 runs | 结果 |
|---|---|---|---|
| ads-ingest | 06:10 | 1 | exit 0，但日志里全是 `curl: (6) Could not resolve host: open.gerpgo.com`、`curl: (28) Resolving timed out after 925249 ms` |
| ads-engine | 07:00 | 1 | exit 0 |
| ads-diagnose | 07:05 | 1 | **exit 1**，`网关响应超过硬截止 600s 仍未返回` |
| ads-attribute | 07:10 | **0** | 从未跑过 |
| ads-converge | 07:15 | 2 | 只跑了手工 kickstart 那两次 |

- `StartCalendarInterval` 在机器**关机**时错过的触发点不会补跑（睡眠中错过的会合并成唤醒后一次，关机不会）。这台 Mac 9 点开机，06:10~07:15 全落在关机区间 → 这条链等于没接线。
- 更糟的是「跑过」也不可信：`ingest.py` 在数据集 FAIL 时**仍然 return 0**，launchd 看到 exit 0 就当成功。当天四张事实表覆盖：campaign 止于 11-17、keyword 止于 11-18、search_term 止于 11-17、placement 止于 11-17 —— 三张缺 D-1。
- 反向证据也在：机器凌晨醒着的时候，engine 在 01:22 / 01:25 / 01:28 / 02:24 连跑了 **4 次**，`engine_run` #99~#103 全是 `window_end=2026-11-15`，`memorial` 也跟着写了 4 条 —— 没有当日去重，等于重复烧模型。

**改法：一个 job，反复问「今天做完了吗」**

`adsdesk/chain.py`（新增）+ `~/Library/LaunchAgents/com.baoyanan.ads-chain.plist`（新增，RunAtLoad + StartInterval 1800s）。七步按依赖顺序串成一条链，每步跑之前先看真实状态：

| 步骤 | 「今天做完了吗」的依据 |
|---|---|
| ingest | 四张 `fact_*_daily` 的 `max(report_date)` 是否都 ≥ D-1（物理覆盖，不看退出码） |
| market | `run_log` 今天有 `status='ok'` 的 `market.*`，且覆盖 `market_datasets()` 当天要的数据集（竞品+品类行情每天、ABA 按周） |
| engine | `engine_run` 今天有 `status='ok'` |
| diagnose | `memorial` 今天有 `agent_state='ok'` |
| attribute | `agent_run(job='attribute')` 今天有 `ok` |
| converge | `converge_run` 今天有 `ok` |
| midship（**opt-in，不在默认链**） | `run_log` 今天有 `status='ok'` 且 `dataset like 'midship%'` |

`midship` 这一步（2026-11-24 接入，见 `midship/README.md`）只注册、不默认跑：它的输入是 `event_inbox` 事件账本，而事件由 ingest / engine 收尾时写入 —— 整链跑完之前当天账本还没闭合，先投影等于把半截事件推给 gbrain，且它一旦失败会把整链标成 `blocked`。所以用法是链跑完后手动补 `python3 adsdesk/chain.py --only midship`。它的完成判定读 `run_log`（`midship` 自己写的账），不读 `chain_run` —— 因为 `run_step` 是「跑完 → 复验 → 才 record」，拿 `chain_run` 当凭据会让第一次成功也判 failed。

`market` 步的采集范围不是写死的 `all`：竞品动作与品类行情每天都要一份新的（动作是「跟上一份快照比」出来的，断一天就比不出那天发生了什么）；ABA 是**周数据**，`aba_weekly` 里已有本周的周键就不再重采 —— 否则每天白花 30 次 `keyword_detail` 额度把同样的 30 个词采一遍。

`chain_run` 表只记「试了几次、错在哪、耗时多少」，**不当完成凭据**；`ok = (退出码==0) and 复验覆盖通过`。

四道保险，全部对着上面的实测问题：

1. **时间窗 09:00~23:00** —— 半夜机器自己醒来不动手，不烧 LLM。
2. **flock 单实例**（`/tmp/ads-chain.lock`）—— ingest 补一天要 10~15 分钟（积加接口 60s/次节流），30 分钟一次的轮询会和它撞车，撞上就本次退出、不排队。
3. **等网络就绪** —— 唤醒瞬间 DNS 常常还没起来，`net_ready()` 每 10 秒试一次 `open.gerpgo.com:443`，最多等 5 分钟。
4. **每天失败次数上限**（ingest 8 / market 3 / engine 4 / diagnose 2 / attribute 2 / converge 2）—— 真坏了就停手，不无限重试烧钱。

**跟旧结构的对照**

| | 旧：五个固定钟点 | 新：一个守夜人 |
|---|---|---|
| 9 点开机后会不会跑 | 不会（错过就没了） | 登录即跑，之后每 30 分钟自查 |
| 断网/超时 | 当天直接放弃 | 下一轮自动重试（有次数上限） |
| 上游失败 | 下游照跑，烧模型审旧数据 | 下游记 `skipped`，等上游修好 |
| 同日重复 | engine 凌晨跑了 4 次 | 当天成功过就不再跑 |
| 补历史空洞 | `--recheck-days 3`，停 4 天以上留永久空洞 | 按四张表的真实缺口算起点，最多补 30 天 |

**实测**：新 job `launchctl print` → `runs=1`、`last exit code=0`；日志 `~/Library/Logs/ads-chain.log` 第一行 `[14:37:51] 另一条链正在跑，本次退出（不排队）` —— RunAtLoad 立刻触发、被 flock 正确挡回，说明锁生效而不是死锁。旧五个 plist 已 `bootout` 并改名 `.plist.disabled`。

**代价与口径**：判定日 = `verifiable_at + 1 天`（ingest 只拉 D-1），比原来晚一天，不是延迟而是数据物理。

### 2.2 判定线随单数变，不是一个数

旧的 `min_clicks` 公式 `ceil(ln(0.2)/ln(1−p0))` 只在**零单**时成立。修完（`engine/facts.py` 新增 `min_clicks_for_orders`）后的真值：

| 观测单数 k | 判定线（点击） |
|---:|---:|
| 0 | 274 |
| 1 | 509 |
| 2 | 727 |
| 3 | 938 |

scope 内每个词的单数都是 0 或 1，所以真实门槛是 **274~509 击**。`lat pulldown` 现在 248 击 1 单，还差 **261 击 ≈ 15 天**。工作台的每条建议必须显示「还差多少」，而不是只显示「未达线」。

### 2.3 五层里只有组合层有证据

## 四、数据契约

### 4.1 新增 5 张表（`adsdesk/api/schema.sql`）

```sql
-- ① 奏折归档。pack_json 从 engine_run 里分出来，因为 engine_run 是运行记录不该塞 30KB JSON。
CREATE TABLE IF NOT EXISTS memorial (
    run_id        INTEGER PRIMARY KEY,
    business_day  TEXT NOT NULL,              -- 窗口末日，如 2026-11-14
    pack_json     TEXT NOT NULL,
    report_path   TEXT,
    agent_state   TEXT NOT NULL DEFAULT 'pending',
                  -- pending | ok | partial | failed（诊断 agent 的状态）
    created_at    TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_memorial_day ON memorial(business_day DESC);

-- ② agent 每次调用都留痕，任何输出都能追到「哪个模型、哪版 prompt、多少 token」。
CREATE TABLE IF NOT EXISTS agent_run (
    agent_run_id  INTEGER PRIMARY KEY AUTOINCREMENT,
    job           TEXT NOT NULL,              -- diagnose | attribute | converge | converse
    run_id        INTEGER,                    -- diagnose 关联的引擎 run
    model         TEXT NOT NULL,              -- 实际用的模型名
    prompt_ver    TEXT NOT NULL,              -- prompts/*.md 的 sha1 前 8 位
    started_at    TEXT NOT NULL,
    finished_at   TEXT,
    status        TEXT NOT NULL DEFAULT 'running',   -- running | ok | failed
    tokens_in     INTEGER, tokens_out INTEGER,
    input_digest  TEXT,                       -- 输入 JSON 的 sha256，用于复现
    output_json   TEXT,
    error         TEXT
);

-- ③ agent 反对规则建议。一条反对一个 decision_id，可以反对多条。
CREATE TABLE IF NOT EXISTS agent_objection (
    objection_id  INTEGER PRIMARY KEY AUTOINCREMENT,
    agent_run_id  INTEGER NOT NULL,
    decision_id   INTEGER NOT NULL,           -- 必须指向已存在的 decision_log 行
    verdict       TEXT NOT NULL,              -- oppose | doubt
    why           TEXT NOT NULL,              -- 为什么反对（人话，一句话）
    evidence      TEXT,                       -- 引用了哪个字段/哪张表/哪条 policy
    created_at    TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_objection_decision ON agent_objection(decision_id);

-- ④ agent 的可验证断言。这是「学习」能成立的地基：没有它，agent 说什么都不算数。
CREATE TABLE IF NOT EXISTS agent_eval (
    eval_id       INTEGER PRIMARY KEY AUTOINCREMENT,
    agent_run_id  INTEGER NOT NULL,
    agent         TEXT NOT NULL,
    claim         TEXT NOT NULL,              -- 一句话断言
    verifiable_at TEXT NOT NULL,              -- 什么时候能验
    method        TEXT NOT NULL,              -- 用什么数据、什么口径验
    expected      TEXT NOT NULL,              -- 预期结果（要能判真假）
    verdict       TEXT NOT NULL DEFAULT 'pending',
                  -- pending | correct | wrong | unverifiable
    actual        TEXT,
    checked_at    TEXT,
    created_at    TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_eval_due ON agent_eval(verdict, verifiable_at);

-- ⑤ 对话 agent 的会话记录（只读问答也要留痕，否则无法审计它说过什么）。
CREATE TABLE IF NOT EXISTS chat_turn (
    turn_id       INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id    TEXT NOT NULL,
    role          TEXT NOT NULL,              -- user | assistant
    content       TEXT NOT NULL,
    cited_tables  TEXT,                       -- assistant 引用了哪些表
    agent_run_id  INTEGER,
    created_at    TEXT NOT NULL
);
```

### 4.3 `pack_json` 扩展（`engine/report.py` 改 3 处）

今天的 `pack_json` 只有 13 个键，**`front[]` 里每条建议只有 11 个字段，没有 calculation / significance / context**。工作台要回答「这条是怎么算的」，必须扩。

```python
# engine/report.py:677 pack_json()
# 改动 1：dec() 增 4 字段
def dec(d):
    return {
        ...原有 11 字段...,
        "decision_id": d.decision_id,              # ← 需要 rules.Decision 补这个字段，或落库后回读
        "calculation": d.calculation,               # 计算链，工作台折叠展示
        "significance": d.significance,             # p_worse/p_better/need_for_orders
        "cooldown_until": d.cooldown_until,
    }

# 改动 2：增 conflicts 明细（现在只有 conflict_count）
"conflicts": [
    {"keyword_text": c["keyword_text"], "campaigns": c["campaigns"]}
    for c in pack.conflicts
],

# 改动 3：questions 增 reason_codes（v1.3 词典要求选项对应原因码）
"questions": [
    {**q, "reason_codes": q.get("reason_codes", [])} for q in pack.questions
],
```

**注意**：`decision_id` 现在 `Decision` dataclass 里没有。两个选法——(a) `rules.Decision` 加一个 `decision_id: int | None = None` 字段，落库时回填；(b) `pack_json` 接受一个 `id_map` 参数。**我选 (a)**，因为 `to_row()` 已经是 dict，加字段零成本，且回读时 `save_decisions` 能拿到 `lastrowid`。

### 4.4 归因窗长度（写进 `agents/attribute.py` 常量）

| 动作类型 | 归因窗 | 理由 |
|---|---|---|
| `raise_budget` / `reduce_budget` / `lower_budget` | 5 天 | 预算变化当天就影响曝光，但报表按天汇总、归因还要回传：3 天窗里有一天是半截数据，实际可用样本只有 1~2 天。5 天是「够判量级 + 不过度拖延」的折中（2026-11-24 由 3 天上调） |
| `reduce_bid` / `raise_bid` | 7 天 | bid 变化要等竞价池重新分配，太短看不出 |
| `add_negative` | 14 天 | 否词影响的是长尾流量，14 天才有足够曝光 |
| `adjust_placement` | 7 天 | 位次溢价生效慢 |
| `harvest_keyword` | 14 天 | 收割新词需要冷启动 |
| `pause_candidate` | 14 天 | 停用是终局动作，要给足观察 |

**每个窗都必须带对照组**：同一时间窗内、同层级、未改动的对象。没有对照组的变化一律标 `evidence_level='weak'`，不进策略库。

### 5.4 关键实现细节

**① `decision_id` 回读**。`save_decisions()` 现在返回 `int`（写入条数）。改成返回 `dict[tuple, int]`（`(rule_id, entity_id, action_type) → decision_id`），`pack_json` 用它填 `decision_id`。

**② `/api/memorial/today` 的合并逻辑**。`memorial.pack_json` 是快照，但审批状态会变。所以：

```python
pack = json.loads(row["pack_json"])
ids = [d["decision_id"] for d in pack["front"]]
live = read_conn.execute(
    f"SELECT decision_id, status, checked_at, checked_by, executed_at, "
    f"reject_reason, reject_reason_code, attribution_due_at "
    f"FROM decision_log WHERE decision_id IN ({','.join('?'*len(ids))})", ids)
for d in pack["front"]:
    d.update(live.get(d["decision_id"], {}))
pack["objections"] = read_conn.execute(
    "SELECT o.*, r.model FROM agent_objection o "
    "JOIN agent_run r USING(agent_run_id) WHERE r.run_id=?", (run_id,)).fetchall()
```

**③ 过期处理**。`EXPIRY_HOURS = 72`，但库里 78 条历史 `proposed` 从未被置 `expired`。工作台启动时跑一次 `UPDATE decision_log SET status='expired' WHERE status='proposed' AND decided_at < datetime('now','-72 hours')`。这是 P1 第一件事，否则审批台会看到 78 条僵尸。

### 7.3 面板③要突出「贴溢价上限」

> **⚠ 2026-11-17 勘误**：本节原写「出价 $0.40 的两个活动 CPC 达 $1.313（3.3×）/ $1.555（3.9×），超过 200% TOS 上限 $1.20，是自己抬自己的价」。**这个结论是错的**，已按 `fact_placement_daily` 实测订正。

真实数据（窗口 2026-10-31~11-13）：

| campaign_id | 活动名 | 位次 | 实际 `bid_adjustment` | 溢价上限 | 点击 | 花费 | 实际 CPC | 占上限 |
|---|---|---|---:|---:|---:|---:|---:|---:|
| 47309998237757 | L3-基础CPC0.4-**头部200%**-lat pulldown machine-Fix | TOS | **280%** | **$1.52** | 102 | $133.91 | $1.3128 | **86.4%** |
| 237761921757002 | L3-基础bid0.4 **溢价1.4** top-lat pulldown-fix | TOS | **350%** | **$1.80** | 50 | $80.87 | $1.6174 | **89.9%** |
| 237761921757002 | 同上 | Other | 0% | $0.40 | 5 | $5.79 | $1.158 | 289% |

三处错：①**把活动名当成真实溢价倍数**——`溢价1.4` 实际 `bid_adjustment=350.0`，`头部200%` 实际 `280.0`，两个名字都过期；②**拿词层 CPC 比 TOS 位次上限**——$1.3128/$1.5546 是 `fact_keyword_daily` 的全位次混合均价，拿平均价对单个位次的顶价，比法本身错；③$1.20/$0.56 两个上限也是从错名字推的，真实是 $1.52/$1.80。

**正确结论**：没有任何活动超溢价上限。真实现象是**两个活动都贴着各自上限在买同一个 TOS 位**（86.4% / 89.9%）。这是「结构上两个活动抢同一个位次」的**成本证据**，不是「互相抬价」的**机制证据**——后者要单活动期对照，现在没有。`Other on-Amazon` 那条 0% 溢价跑出 $1.158（289%）是唯一真超上限的行，但只有 5 击，属噪声，不作结论。

## 八、四个 agent 岗位

### 8.1 共同契约（三张表 + 一条铁律）

**铁律：agent 不产生建议。** 它只能：
- 对已存在的 `decision_id` 说 `oppose` 或 `doubt`（写 `agent_objection`）
- 提出疑问清单（写进 `pack_json.questions` 的候选，由工作台渲染）
- 提出可验证断言（写 `agent_eval`）

## 九、归因闭环

### 9.1 从打钩到结论的完整时序

```
T+0   用户打钩          decision_log.status='approved', checked_at=T0
T+0   生成执行单        ticket 表新增，status='approved'
T+1h  用户手改后台       ——
T+1h  用户点「已改」     status='executed', executed_at=T1,
                        attribution_due_at = T1 + 窗长（按动作类型）
T1+窗 归因 agent 扫到   status='executed' AND attribution_due_at <= today AND outcome_filled_at IS NULL
T1+窗 写 outcome_7d_json / outcome_14d_json + outcome_filled_at
T1+窗 写 agent_eval（这次归因的断言）
T1+2周 收敛 agent 回填 agent_eval.verdict
```

### 9.2 为什么归因窗不能从打钩起算

今天 `decision_log` 里有 78 条 `proposed` 从未被处理，5 条 `proposed` 卡着，6 条 `rejected`。**用户打钩 ≠ 广告后台真改了。** 如果从打钩起算，中间「批了但没改」的时间会被算进「改动后的效果」，系统性稀释效应。

所以 `executed_at` 必须由用户显式点「已改」触发。这是本次设计里唯一一处要求用户多做一个动作的地方，值得。

### 9.3 弱证据不进策略库（代码强制）

```python
# agents/attribute.py
if evidence_level != "weak":
    # 才允许写 policy 提案
    pass
else:
    # 只写 outcome_*_json，不写 policy，不写 agent_assumption
    pass
```

## 十、失败降级与可观测

### 10.1 四层降级

| 失败点 | 降级行为 | 用户看到 |
|---|---|---|
| 诊断 agent 超时/报错 | 用 `report._build_questions()` 的硬编码问题 | 奏折完整，`agent 反对` 区显示「今天没跑成」+ 错误摘要 + 重试按钮 |
| 归因 agent 失败 | `outcome_*_json` 留空，下次重跑 | 归因页显示「N 条待归因，上次运行失败」 |
| 网关不可达 | 三个 agent 全跳过，写 `agent_run.status='failed'` | 顶部黄条「agent 网关不可达，规则引擎正常」 |
| 数据库锁 | 读操作走 WAL 只读连接，写操作重试 3 次后 503 | 前端 toast「写库失败，请重试」 |

**核心原则：agent 是附加价值，不是单点故障。** 与 P1.0「学习层崩溃不阻断报告」同一思路（`engine/facts.py` 的 `_safe_layer_evidence` 已实现该模式）。

### 10.2 可观测

- 每次 agent 调用写 `agent_run`，含 `input_digest`（输入 JSON 的 sha256）。任何一次输出都能用 digest 复现。
- `prompt_ver` = `prompts/*.md` 的 sha1 前 8 位。改 prompt 会变，能追「哪版 prompt 出的这个结论」。
- 前端「Agent 面板」显示：最近 20 次运行、成功率、平均 token、evaluation 得分（correct / (correct+wrong)）。

## 十三、风险与明确不做

### 风险

| # | 风险 | 应对 |
|---|---|---|
| R1 | 诊断 agent 出的问题质量差，用户每天要跳过 | 上线第一周只**记录不展示**（`agent_state='shadow'`），对比硬编码问题与 agent 问题，命中率 > 80% 才切主 |
| R2 | agent 反对变成噪音（每条都反对） | 硬约束：单次 `objections` ≤ 3 条；连续 3 轮反对同一 `decision_id` 后强制闭嘴 |
| R3 | `pack_json` 扩字段导致 md 渲染变慢 | 实测 9287 bytes → 预计 20KB，可接受；若超 100KB 改成 md 只读摘要、json 存全量 |
| R4 | 前端手写 SVG 出视觉 bug | 先做 P2 的 funnel 一个面板验证，通过再复制到其他面板 |
| R5 | `decision_id` 回填改 `save_decisions` 返回值，破坏现有调用 | 保持返回 `int` 不变，另加 `save_decisions_with_ids()` 新函数，`run.py` 调新的 |
| R6 | 78 条僵尸批量置 `expired` 可能误伤 | 加 `WHERE status='proposed' AND decided_at < datetime('now','-72 hours')`，且先备份 |
| R7 | 端口 5273/5274 被后续进程占用 | 启动时检测，被占则报错并提示改 `adsdesk/api/config.py` 的 `PORT` 常量 |

### 明确不做

- 不做登录/权限（本机单用户）
- 不做移动端适配（桌面 1280 起）
- 不做暗色主题（P1 只做浅色）
- 不做多账户切换（scope 硬编码 `JL-高位下拉` / `B0GLYW51HY`）
- 不做自动执行（写权限未开）
- 不做 agent 生成建议（铁律）
- 不做 embedding 语义聚类（网关 `/v1/embeddings` 返回 404）
- 不做 `rank_snapshot` 采集（无数据源）
