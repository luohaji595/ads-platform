## 二、这次补了什么（相对验收前）

### 1. 市场采集器修好了（原来卡了整条链 3 天）

**现象**：`ingest/market.py` 每天失败，`category_products` 报 `An error occurred invoking 'category_products'`。当时判断是「node_id 23533924011 死了」，实际不是。

**真因**：`category_products` 必须带 `query_start` + `query_date`，且窗口要 3–40 天、结束日 ≤ 今天−2。不带日期就直接报错；结束日传今天或明天，网关不报错但返回空。

**修法**（`ingest/market.py:83` `_top_window()` + `:716` 取窗 + `:722` 传参）：按真实今天算出 `[今天−4, 今天−2]` 窗口传进去；顺带加了两层防御 —— 单节点返回空就跳过该节点并记 note，所有节点都空就整批不写并抛错（半截数据比没数据更坏）。

**效果**：`market_daily` 2026-11-23 有 asin 10 行 + category 1 行（旧代码这一行永远缺）。`aba_weekly` 到 2026-W47 共 30 行，`market_daily` 共 34 行。

### 2. 奏折里的「agent 反对区」从零写出来

计划书三处（`:417` 链路图、`:1113` 降级表、`:1173` P3 验收）都要求奏折 md 有这一区，但 `engine/report.py` 里一行相关代码都没有，诊断 agent 是纯影子模式（只写库不改报告）。

**设计**：engine 渲染时先写一个**带定位标记的空区块**（`<!-- AGENT_OBJECTIONS_START -->` … `END`），diagnose 落库成功后**原位替换**。没有选「diagnose 重渲染整份」——engine 的 Facts 早不在内存了；也没有选「正则猜标题」——标题文案以后会改，标记不会。

**现在的样子**：有反对时渲染「诊断 agent 今天提了 N 条（反对 x / 存疑 y）。它不提案，只质疑」+ 每条原话 + `<details>` 折叠它自己下的兑现承诺表；网关挂了渲染「诊断 agent **今天没跑成**：{错误摘要}」；没跑渲染「今天还没跑，规则引擎的结论不受影响」。

**踩过的坑（已修）**：`importlib` 动态加载 `report.py` 时，`@dataclass` 要按 `__module__` 回 `sys.modules` 取模块字典，不先登记就报 `'NoneType' object has no attribute '__dict__'`。

### 3. 封了一个跨库写入漏洞（数据安全）

**现象**：生产奏折的反对区被写成「今天没跑成：HTTP Error 429」，但生产库里没有对应的失败记录。

**真因**：子代理在 `/tmp/xxx.sqlite3` 副本上跑 diagnose，而 `memorial.report_path` 存的是**生产 md 的绝对路径**，替换函数照着写，把副本的失败写进了生产报告。

**修法**：`_report_write_guard()` 两道闸 —— ① `pragma database_list` 的库路径必须就是生产库；② md 路径必须在项目根下。任一不满足返回 `skipped:…`，一个字节都不写。

### 4. 模型网关全通道排查（原来诊断整个跑不动）

**根因**：`auto/*` 与 `codearts/*` 背后是 CodeArts，**积分已耗尽**（`HTTP 400` + `TM.00001050`）。`duanyan/*` 是**按 max_tokens 掐额度**的 —— 8 token 能过，4000 就 `429 书生端砚: quota exceeded`，跑不动 48000 预算的诊断。

**修法**：`gateway.py` 改成多通道降级链，首选 `trae-cn/deepseek-v4.1-flash-max`，备选 `scnet/DeepSeek-V4.1-Flash-1017-Event`、`opencode-zen-free/*`、`trae-cn/glm-5.3-flashx`，`auto/*` 留作最后兜底。新增 `chat_chain()`：按链依次试，第一个答出来的就是结果，全挂才抛错。

**效果**：诊断 agent 现在 6 分钟出 5 个问题 + 2 条存疑，`agent_run` 有 ok 行、tokens 16586/28455。

**顺带验了降级线**：`ADS_GATEWAY_BASE=http://127.0.0.1:9999/v1` 跑 diagnose → 奏折照常出，反对区显示「今天没跑成」，符合计划书 `:1222` 的要求。

### 5. 位次（排名）链路从零接通

计划书原本写着「不做 `rank_snapshot` 采集（无数据源）」。这次用 Sorftime 的 `product_ranking_trend_by_keyword` 破了局：

- `ingest/rank.py`（808 行）：采位次快照 + 种目标。`placement_of()` 把 Organic 归自然位、SP Ad 归广告位、**Video Ad / brand ad 直接跳过**（视频位品牌位不是 bid 能调的轨道）。
- `rank_snapshot` 加了**唯一索引** `ux_rank_snapshot_ident`（keyword_id, observed_at, placement, asin, page, position）。这里有个隐蔽的坑：`migrate.py` 的建索引循环原来一律 `create index`，把 `UNIQUE` 静默降级成普通索引 —— 名字叫 `ux_` 却拦不住重复，比没有更糟。已给循环加 `UNIQUE` 前缀支持。
- `rank` 进了守夜人链，排在 `engine` 之前（否则 R31 读的是昨天的位次）。

**数据现实（重要，别当 bug）**：12 个目标词只有 6 个有位次数据，另 6 个（`rowing machine for home`、`rowing machines for home`、`ab machine foldable`、`row machine for home`、`desk treadmill`、`adjustable dumbbells`）直连数据源返回 `No relevant data.`，`product_traffic_terms` 前 40 个词也一个都不含。**广告侧确实有曝光，但源端没有这个 ASIN 在这些词下的位次记录**。面板渲染 `—`，没写假 0。

### 6. R31「没数据」拆成两句不同的话

原来 R31 对「算不出来」只有一句话「关键词不在本窗口数据里」。实测 12 个目标词里只有 2 个在引擎作业范围内，另 10 个属于别的投放组合 —— 两句话结论完全相反：**前者是数据缺口，后者是范围设定**。混在一起会让主人以为位次采集坏了。

**修法**：`facts.keyword_portfolio_map()` 反查该词所在活动的投放组合，阀零分三支输出：「不在本次作业范围内（组合 XXX）」、「该活动没归进任何投放组合」、「真没投过」。实跑 run #120：12 条压制 = 9 条范围外 + 1 条观测过期 + 1 条 ACOS 闸 + 0 条「没数据」。

### 7. 修了两个「僵尸建议」与「夹具腐坏」类缺陷

- **僵尸清扫口径**（`engine/run.py:202`）：原来只收「今天零点前过期」的，漏掉今天上午过期的 —— 已失效、又不在今天这份奏折里，却还占着待批队列，主人看到一条点不动的建议。改成比完整时间戳。实跑清掉 decision 177。
- **回归夹具腐坏**（`engine/test_r31.py` case 7）：夹具硬编码了真库里的历史行，而窗口会随数据最新日期右移，某天那行整段滑出窗口，用例就静默退化成「词不在窗口里」，挂在一个与规则无关的原因上。改成按当前窗口现造数据（新增 `add_kw_daily()`）。教训写进注释：**回归夹具不许依赖会漂移的窗口边界**。

## 四、需要你拍板的三件事

1. **12 个位次目标的 goal 全是「第 1 页第 4 位」** —— 这是种目标时照抄 schema 默认，没按各词的实际起跑位校准。`lat pulldown` 现在在第 3 页第 22 位，让它 5 次连续到第 1 页第 4 位，规则会一路加价到 `max_bid` 触顶。**建议按词分级**：头部词（已在第 1 页）设第 4 位，腰部词设第 2 页前 8 位，尾部词先只观测不推。

2. **6 个词拿不到位次是数据源硬底，不是采集器问题**。如果你想让这 6 个词也进位次管理，只能换数据源（第三方插件/自建爬虫）。要么接受「6 个词只管广告侧、不判位次」，要么告诉我换源。

3. **诊断 agent 的 `_REFUTE_ON` 题号方向映射是按出题语义推的**，计划书没给表。意思是：Q01 判「变差才算证实」、Q03/Q04/Q05 判「变好才算证实」、Q08 判「变差才算证实」。这条影响假设转策略的方向对错，建议你确认一遍语义。
