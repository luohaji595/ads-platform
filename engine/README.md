# 广告规则引擎（engine）

从积加报表算出「今天该动哪几个东西」，产出待批清单。**它不写后台。**

数据只有一个来源：积加。所有数字都是 `engine/run.py` 从 `ingest/data/ads.sqlite3` 里算出来的，
没有任何一项由人填写。改过什么，也是靠「每天拍一张配置快照，和昨天比」自动发现的。

---

## 一、三层结构

```
L2 动作层  rules.py    九条规则 → 建议（改 bid / 加否词 / 收割 / 加预算 / 调位次加价 / 卡位）
                          ↓ 每条建议必须过五道保护
L1 事实层  facts.py    阈值从本店数据现算：判定线、盈亏平衡、地板、CPC 校准系数
                          ↑
L0 观测层  snapshot.py 每天拍配置快照 → 和上一份比 → 变更流水
```

**为什么要分三层**：所有商业工具（积加、Scale Insights、优麦云）的参数都是写死的默认值，
因为它们的用户是月花 5 万美元的成熟账户。本账户日花 $190、单词年化 668 次点击，
照抄那些默认值的后果不是「不够优化」，是**误杀**。

所以这里的规矩是：**任何阈值都不许写死，必须每次从本店数据重算**，并且把计算过程留在报告里。

---

## 二、怎么跑

```bash
cd engine

python3 run.py                      # 正常跑：拍快照 → 算事实 → 跑规则 → 写库 → 出报告
python3 run.py --dry-run            # 只看结果，不写库
python3 run.py --window-days 21     # 换分析窗口（默认 14 天）
python3 run.py --target-acos 0.35   # 换目标 ACOS（默认 30%）
python3 run.py --no-snapshot        # 跳过快照（调试用）
```

输出两样东西：

1. 终端四行摘要
2. `engine/reports/YYYY-MM-DD-待批清单.md`（文件名里的日期是**排除归因窗口后的最后一天**，不是数据最新日）

数据库用的是 `ingest/data/ads.sqlite3` 同一个库，engine 的表和事实表可以直接 join。

## 三、报告怎么读

| 节 | 讲什么 |
|---|---|
| 一、账户现在什么状况 | 漏斗指标 + 盈亏平衡转化率 + 判定线 + CPC 校准系数 + 出价地板 |
| 二、今天该做什么 | 动作表：做什么 / 对象 / 现在 / 改成 / 影响金额 / 证据够不够 |
| 三、每条建议是怎么算出来的 | 一句话理由 + 可展开的完整计算链（每一步的公式、参数、结果、含义） |
| 四、为什么大部分词没动 | 被五道保护拦下的原因和对象 |
| 五、样本不够，先记着 | 只能观察不能动的 |
| 六、后台配置最近变过什么 | 快照 diff 的结果，以及这个结果可不可信 |

**读报告的顺序建议**：先看第一节那个「目标不可达」的警告块，再看第二节的动作表，
第三节只在你想质疑某条建议的时候展开。

## 四、五道保护（为什么大部分词不动）

| 保护 | 拦什么 | 本账户实测拦下 |
|---|---|---|
| 目标可达性 | 全店 CVR < 盈亏平衡线时，降 bid 解决不了问题 | 输出全局告警 |
| 置信度门控 | 点击不够判定线（本账户 88 次）的建议降级成「只看不动」 | — |
| 地板校验 | 算出的目标价低于地板时，不当降价建议而是标「降到底价」或「建议停用」 | 1 条 |
| 花费闸门 | 花的钱还不到一单的利润，动了也是噪声 | 40 条 |
| 核心词保护 | 每单成本明显优于账户平均的词，ACOS 再高也不许降（ACOS 高可能只是客单价低） | 3 条 |

## 五、九条规则

| 编号 | 名字 | 干什么 |
|---|---|---|
| R30 | 目标可达性告警 | 算盈亏平衡 CVR，和实际比，不可达就明说「这不是出价能解决的」 |
| R01 | 降出价 | 三分支算目标 bid（有销售额 / 有订单无销售额 / 无订单），过地板校验 |
| R03 | 加出价 | 四道闸：有订单、CVR 过盈亏平衡线、目标价高出 15%、活动预算没打满 |
| R02 | 否词候选 | 跨活动按搜索词聚合，保护已转化的词及其子串超串 |
| R04 | 收割成词 | 出单 ≥2 次的搜索词提成关键词，初始 bid = 历史平均 CPC |
| R08 | 加预算 | 预算打满且表现优于账户平均的活动 +20% |
| R09 | 调位次加价 | **按活动 × 位次**，参照系是同一活动内部，不是全店 |
| R21 | 拓词入组 | 有点击零单的词列为候选，固定标「未验证」 |
| R31 | 卡位 | 按「当前排名 vs 目标排名」推 bid 或 TOS 加价，由排名反推，不由表现反推 |

**执行顺序**：R30 → R01 → R08 → R03 → R31 → R09 → R04 → R02 → R21。
R30 先跑，因为它决定后面敢不敢动；R08 在 R03 之前，因为预算打满时加价没有意义。
R31 排在 R03 之后：被卡位接管的关键词，R01/R03 会自己让路（见下面第 7 条坑）。

## 六、几个必须知道的坑

**1. 归因窗口**。最近 2 天的点击还没回完单，任何判据都要排除。`--exclude-days` 可调 1-7。

**2. 零值语义不一致**。campaign 表里无单的 ACOS 是 `0.0`，searchterm 表里是 `null`。
判「有没有单」只能看 `ads_orders` / `clicks`，**绝不能看 ACOS 或 CPA**。

**3. 回补数据不是历史**。ingest 在 2026-11-14 一次性回补了 11-01~11-13 十三天，
如果 `bid` 是拉取时的当前值，这十三行携带的都是 11-14 那天的 bid。
`snapshot.py` 用 `run_log.started_at` 记录「这批数据是什么时候被观测到的」，
两次快照观测时刻相同就标 `reliable=0`，不拿它当变更证据。

**4. 位次加价是每个活动单独设的**，没有「全店 TOS 加价」这个开关。
按 placement 汇总出的建议没法执行，所以 R09 做到「活动 × 位次」粒度。

**5. 加价为 0% 时无法再降**。这时只能去调基础出价（R01），R09 会明说而不是给假建议。

**6. 出价地板是粗估的，不是测出来的**。出价和出量被「关键词本身有多热」混在一起了：
有的词出价 $0.83 却 14 天只有 15 次点击（不是价格问题，是没人搜）；
有的词出价 $0.65 却有 519 次点击（不是便宜，是热门词）。
要真测地板只能做对照实验。

**7. 卡位是唯一「不看表现」的规则**。别的规则都在问「这个对象赚不赚钱」，
R31 只问「现在排第几、目标第几」。所以它必须有三道闸，否则会一路加价烧钱：
①**ACOS 闸** —— 窗口 ACOS 超过 `target × acos_guard_mult`（默认 1.5 倍）就停卡转人工；
零单时改看「花费是否超过 `aov × 目标ACOS × 倍数`」（因为 ACOS=0 是零值陷阱，不是表现好）。
②**加价次数上限** `max_pushes`（默认 6）—— 累计加价次数到顶就停，不无限追。
③**与 R01/R03 互斥** —— 同一个词被 `rank_target` 接管后，R01/R03 直接 suppress，
理由是「卡位接管」。不互斥的后果是：上午 R01 判它该降价、下午 R31 判它该加价，
一天之内互相打脸，还留下两笔都执行过的记录。
优麦云原版没有 ①②③ 这三道闸，这是本引擎补的。

**8. 卡位按「批次」判排名，不按「行」**。插件一次抓取会把前 N 位逐个 ASIN 写成多行，
同一个 `observed_at` 就是同一批次。只取第一行会拿到「排在第一位的那个人」，不是自己 ——
自己的排名判成别人的，自家另一条记录还会被误判成自我竞争。所以 `rank_state` 按
`(keyword_id, observed_at)` 分批，批内找 `asin` 等于卡位对象的那个行；
找不到 = 本次抓取深度内没看到自己 = 位次比抓取深度还深，按「未到位」处理并在计算链里写明。

**9. 卡位的 TOS 加价不走 `campaign_placements`**。那个函数带 `min_cost/min_clicks` 门槛
（为「位次值不值得投」设计），刚开不久的活动会被过滤掉，读不到配置而误判「无数据」。
实测 campaign `46818486452618` 窗口内 TOS=150% 连续 13 天，但因 TOS 位点击不足 20 被门槛吃掉。
卡位只关心一个活动的一个位次，走 `rank_tos_pct()` 直接读 `fact_placement_daily`。

## 七、它不做什么

- **不写广告后台**。执行要走审批（`ticket` 表），且每次改动前留快照可回滚。
- **不假装知道最优值**。算不出来就说算不出来，标 `observe`。
- **不隐藏样本不足**。样本不够就降级，不硬给结论。
- **不判断「该修广告还是修 Listing」**。这一层在报告第一节的警告块里交给人。

## 八、表结构

见 `schema_v2.sql`。九张表 + 一个视图：

| 表 | 干什么 |
|---|---|
| `config_snapshot` | 每个**观测点**一张配置快照（campaign 的预算/状态、keyword 的 bid/serving_status、placement 的加价）。身份是 `snap_ts`（观测时刻，取自 `MAX(ingested_at)`）而不是报表日期 —— 用日期当身份时同一天跑 N 次 ingest 只会互相覆盖，日内变更根本存不下来 |
| `config_change_log` | 相邻两个**观测点**的差异，`reliable=1` 才算真变更（两个点的真实观测时刻不同） |
| `config_diff_state` | 哪些观测点对已经算过 diff。零变更的点对在 `config_change_log` 里没有行，靠流水判「算过了」会每轮重算 |
| `decision_log` | 每条建议一行，含 `context_json` / `calculation_json` / `significance_json` 三个必填字段 |
| `ticket` | 审批单，把同一批建议打包给人批 |
| `engine_run` | 每次运行的元信息 |
| `rank_target` | 卡位配置：卡哪个 ASIN 到第几页第几位、加价方式与步长、三道闸参数 |
| `rank_snapshot` | 排名观测（插件/上游写入）：一次抓取多行，同 `observed_at` 为同一批次 |
| `v_open_decisions` | 还没批的建议，按置信度和影响金额排序 |

`calculation_json` 存的是**计算链不是结论** —— 三个月后回来质疑「当时凭什么这么算」，能一步步复算出来。
